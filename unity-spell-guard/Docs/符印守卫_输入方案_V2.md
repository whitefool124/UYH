# 符印守卫 输入方案 V2

## 一、文档目的

这份文档用于更新《符印守卫》的整体输入方案。

当前版本的输入逻辑明显偏向“鼠标式”或“空中光标式”设计：

- `Point` 负责菜单焦点
- `Point` 负责视角控制
- `Point` 高位保持负责前进
- 部分交互仍建立在视口坐标和指向区域上

这种方案虽然适合快速搭原型，但当项目开始引入关卡、地图、移动和更完整的战斗体验后，会暴露出以下问题：

1. 对摄像头位置和玩家站位过于敏感
2. `Point` 手势承担职责过多，调试复杂度高
3. 输入更像“空中鼠标”，不像“游戏控制器”
4. 玩家需要理解屏幕空间，而不是理解动作语义

因此，V2 的核心任务不是继续扩手势数量，而是把输入哲学从“指哪里”升级为“做什么”。

## 二、V2 核心输入哲学

### 2.1 从鼠标式输入转向手柄式输入

V2 输入方案的核心思路是：

- 少依赖 `Point` 这类空间指向手势
- 多依赖手势本身的动作内容和离散语义
- 让玩家记住“动作命令”，而不是“镜头坐标”

也就是说，本项目的输入应更接近：

- 手柄按钮
- 动作游戏输入
- 格斗游戏离散指令

而不是接近：

- 鼠标点击
- 屏幕光标
- 第一人称精确瞄准

### 2.2 输入设计原则

V2 后续所有输入设计必须遵守以下原则：

1. 手势优先表达动作语义，而不是表达屏幕位置
2. 输入优先采用离散触发，而不是高精度连续映射
3. 菜单、移动、战斗三套语义都要能在摄像头位置变化下保持可用
4. 同一动作不应承担多个平级核心功能
5. 镜头和地图设计应主动配合手势系统，而不是反过来要求玩家做精密瞄准

## 三、当前版本存在的结构问题

基于当前 Unity 实现，输入方案中 Point 的依赖点非常高。

### 3.1 当前 Point 依赖位置

#### 菜单与界面

`SpellGuardFlowController` 当前通过 `snapshot.ViewportPosition` 计算光标位置，再根据区域命中来完成 `focusedKey` 和 `dwellKey` 逻辑。

这意味着：

- 当前菜单系统本质是“手势光标 + 停留确认”
- `Point` 是 UI 的主交互手段

#### 角色与镜头

`FpsGestureMotor` 当前要求：

- `Point` 控制视角偏移
- `Point` 高位保持触发前进

这意味着：

- 当前移动系统高度依赖视口位置
- 角色控制更像“空中鼠标控制 FPS 镜头”

#### 动态动作系统

当前动态层中还有 `PointToFist`，这进一步强化了 `Point` 在整套系统中的中心地位。

### 3.2 这会带来的问题

1. 摄像头位置变化会显著影响体验
2. 玩家距离镜头远近变化会影响视口阈值判断
3. 菜单、导航、战斗三条链路都被 `Point` 绑定，调试成本极高
4. 游戏会更像“体感鼠标系统”，而不是“手势控制游戏”

## 四、V2 输入目标

V2 要实现的不是“彻底删除 Point”，而是：

### 4.1 新目标

- 让 `Point` 从主控制手势退居次要或备用地位
- 建立以离散动作手势为核心的主输入体系
- 让菜单、选关、移动和战斗都更接近“手柄式操作”
- 降低输入对摄像头空间关系的依赖

### 4.2 新定位

V2 中应当把输入划分为：

1. 系统交互输入
2. 地图 / 移动输入
3. 战斗施法输入
4. 高阶应急输入

这四层都应优先依赖“动作内容”，而不是“指向位置”。

## 五、V2 整体输入方案

## 5.1 系统交互输入

系统交互用于：

- 主菜单
- 选关
- 路线选择
- 设置调整
- 结算确认

### 建议输入方式

| 输入 | 功能 | 定位 |
|---|---|---|
| SwipeLeft | 切换到前一个选项 | 系统导航 |
| SwipeRight | 切换到后一个选项 | 系统导航 |
| Fist Hold | 确认 / 进入 / 激活 | 系统确认 |
| OpenPalm Hold | 返回 / 取消 | 系统返回 |

### 设计说明

这套逻辑不依赖屏幕指向，而更像：

- 左右切选项
- 一个确认键
- 一个返回键

本质上更像手柄，而不是鼠标。

### 菜单表现建议

菜单界面不再强调“按钮坐标”，而应改为：

- 横向或纵向高亮切换
- 当前选项高亮明显
- 左右挥动切换焦点
- 握拳确认
- 张掌返回

如果需要更强世界观表达，可以做成：

- 法阵轮盘菜单
- 符文列表菜单
- 路线节点轮换菜单

总之，不再做“空中指向按钮”的 UI。

## 5.2 地图与选关输入

地图输入用于：

- 章节选关
- 节点路径选择
- 进入下一房间
- 事件节点确认

### 建议输入方式

| 输入 | 功能 |
|---|---|
| SwipeLeft | 选择左侧路线 / 上一个节点 |
| SwipeRight | 选择右侧路线 / 下一个节点 |
| Fist Hold | 确认进入当前节点 |
| OpenPalm Hold | 返回上一层地图 |

### 设计说明

地图不需要做成自由光标点击，而应做成：

- 节点式选择
- 环状切换
- 一次只高亮一个目标点

这既符合手势输入特点，也更适合毕业设计原型的范围控制。

## 5.3 移动输入

V2 中，移动系统不应继续建立在 `Point` 控制视角、`Point` 高位保持推进 的主逻辑上。

移动应改为“离散位移 + 低频推进”方案。

### 建议输入方式

| 输入 | 功能 | 说明 |
|---|---|---|
| SwipeLeft | 左闪 / 左侧步 | 基础横向位移 |
| SwipeRight | 右闪 / 右侧步 | 基础横向位移 |
| PushForward / Forward Thrust | 前冲 / 突进 | 接近目标、穿越空间 |
| OpenPalm Hold | 稳定 / 防御停步 | 暂停推进或进入防御姿态 |

### 当前阶段建议

如果当前代码与识别条件尚不足以稳定支持 `PushForward`，可以先把移动收敛为：

- 左闪
- 右闪
- 自动向目标推进的场景式移动

也就是说，先让“横向换位”成立，再做“主动前冲”。

### 移动设计思路

移动不再是连续摇杆式导航，而是：

- 换位
- 躲避
- 贴近
- 保持

这种模式更像动作游戏中的：

- Step
- Dodge
- Dash

而不是 FPS 的精细行走控制。

## 5.4 战斗施法输入

战斗输入仍然保留当前最稳定的静态法术组。

### 建议保留

| 输入 | 功能 | 定位 |
|---|---|---|
| Fist | 火焰术 | 主输出 |
| VSign | 冰霜术 | 控场 |
| OpenPalm | 护盾术 | 防御 |

### 设计原则

- 三法术继续作为基础核心输入
- 每个静态法术都保留确认窗口
- 玩家主要依赖这三项完成战斗主循环

### 为什么战斗层不大改

因为当前项目里最成熟、最直接、最易解释的部分，正是这组三法术映射。

V2 输入升级的重点不在于重做法术，而在于重做：

- 菜单输入
- 地图输入
- 移动输入
- 镜头与战斗关系

## 5.5 高阶应急输入

高阶层用于在高压战斗中提供更快的响应，不承担基础教学职责。

### 建议保留

| 输入 | 功能 |
|---|---|
| Snap | 快速火焰术 |
| SwipeLeftToRight | 预留：快速冰霜或特殊位移 |
| SwipeRightToLeft | 预留：快速护盾或特殊位移 |

### 当前建议

V2 阶段只建议稳定 `Snap` 作为唯一明确高阶动作。

左右挥动已经被系统层和导航层大量使用，如果同时让它承担高阶施法，会显著提高状态切换与误触复杂度。

因此：

- `Snap` 保留为高阶施法输入
- `Swipe` 优先服务系统导航和移动
- 快速施法型 `Swipe` 暂缓，等状态机成熟后再引入

## 六、镜头与战斗假设更新

Point 弱化后，镜头系统也必须一起调整。

### 6.1 不再追求鼠标式精确瞄准

V2 不建议继续把角色战斗定位成：

- 第一人称精确瞄准
- 手势控制光标式视角
- 玩家负责所有角度控制

这会反向逼迫输入继续依赖 `Point`。

### 6.2 建议改为“弱手动镜头 + 强辅助镜头”

V2 更合适的镜头方向是：

- 镜头默认面向当前主要威胁区域
- 镜头自动保持战斗目标大致位于前方
- 玩家主要做的是闪避、施法、推进，而不是精调角度

### 6.3 更适合的战斗空间

V2 更适合以下战斗空间：

- 房间式遭遇战
- 半固定方向战斗
- 小规模 arena
- 走廊推进

而不是开放式 FPS 漫游战斗。

## 七、V2 手势集合建议

综合可玩性、稳定性和后续落地性，建议当前版本的主手势集合定为：

### 7.1 主集合

- `Fist`
- `VSign`
- `OpenPalm`
- `SwipeLeft`
- `SwipeRight`
- `Fist Hold`
- `OpenPalm Hold`
- `Snap`

### 7.2 次级 / 备用

- `Point`

### 7.3 Point 的新定位

V2 中，`Point` 不再作为主交互核心，而仅保留为：

- 调试输入
- 训练模式辅助输入
- 某些过渡阶段的兼容手段

也就是说：

`Point` 从“主控制轴”降级为“次级辅助输入”。

## 八、对现有代码结构的影响

这套方案不是纯策划层口号，它直接意味着当前代码结构中的若干模块需要调整。

### 8.1 `SpellGuardFlowController`

当前大量依赖：

- `ViewportPosition`
- `focusedKey`
- `dwellKey`
- `GetFocusedRegion(cursor)`

V2 方向下，这一层应改为：

- 当前焦点索引
- 左右切换焦点
- 确认 / 返回

也就是从“光标命中”改成“控制器焦点切换”。

### 8.2 `FpsGestureMotor`

当前逻辑是：

- `Point` 控视角
- `Point` 高位保持前进

V2 方向下，应改为：

- 左右闪避
- 前冲 / 推进动作
- 镜头辅助而不是完全手动

### 8.3 `GestureSpellCaster`

这一层变化最小。

静态三法术映射应保留，高阶动作中只保留 `Snap` 作为最小快速输入即可。

### 8.4 调试与反馈层

`DebugHud` 和 `MotionGestureFeedbackBoard` 中的反馈重点也需要更新：

- 弱化视口位置显示的中心地位
- 强化当前输入模式、当前动作状态、当前离散命令的反馈

## 九、分阶段落地建议

为了控制风险，建议按三个阶段推进。

### 9.1 第一阶段：系统层去 Point 化

目标：

- 菜单、选关、结算不再依赖光标式 Point

做法：

- `SwipeLeft / SwipeRight` 切换焦点
- `Fist Hold` 确认
- `OpenPalm Hold` 返回

### 9.2 第二阶段：移动系统去 Point 化

目标：

- 去掉 Point 控视角 / 高位前进的主逻辑

做法：

- `SwipeLeft / SwipeRight` 负责闪避换位
- 增加一个前冲 / 推进动作
- 镜头改为弱手动或半自动辅助

### 9.3 第三阶段：战斗层与高阶层收束

目标：

- 战斗稳定建立在三法术 + 一个高阶动作之上

做法：

- 保留 `Fist / VSign / OpenPalm`
- 保留 `Snap`
- 暂缓 `PointToFist` 和 `OpenPalmSlap*`

## 十、最终结论

《符印守卫》V2 输入方案的核心不是“再做一套新手势”，而是更新项目的输入哲学。

总结如下：

1. 项目应从“鼠标式体感输入”转向“手柄式离散输入”
2. 菜单与地图交互应从光标指向改为焦点切换与确认返回
3. 移动应从 Point 连续控制改为闪避、位移、推进等离散动作
4. 战斗层保留三法术静态输入，作为系统稳定核心
5. 高阶层只保留少量真正有价值的快速动作，优先保留 `Snap`
6. `Point` 不再作为主控制轴，而退居辅助与过渡地位

如果这套方案成立，那么《符印守卫》的输入系统就会更像一个真正的游戏控制器系统，而不是一个依赖摄像头空间关系的体感鼠标系统。这会让项目更稳定、更像游戏，也更适合做关卡制、地图推进和战斗体验的持续扩展。
