# 论文风险补全实验规划：YOLO 证据与性能指标

## 1. 目标

本文档用于把论文准备稿中两个主要风险转成 Unity 项目内可落地的补强任务：

1. **YOLO 训练/检测实验证据不足**：避免论文算法贡献被质疑。
2. **真实性能指标尚未系统统计**：避免无法支撑“实时、低延迟、稳定交互”等结论。

规划原则：不把当前项目临时扩大成完整深度学习训练平台，而是在现有 Unity + Python bridge + UDP 外部桥接基础上，补齐“可复现、可截图、可写入论文表格”的最小实验闭环。

## 2. 当前可复用基础

### 2.1 已有 YOLO / 外部检测入口

当前 `bridge/mediapipe_udp_bridge.py` 已支持：

- `--enable-yolo`
- `--yolo-model`
- `--yolo-conf`
- `--yolo-padding`
- `YoloPersonDetector`
- YOLO 检测框裁剪后再送入 MediaPipe Hands / Pose
- UDP packet 中通过 `source` 标记 `yoloMediapipeBridge`

当前 `bridge/start_offline_gesture_test.py` 已支持：

- 指定离线视频 `--video`
- 指定 UDP 目标 `--host` / `--port`
- 启用 `--enable-yolo`
- 启用 `--enable-pose`
- 指定 YOLO 模型与置信度

这说明论文不必从零实现 YOLO 接入，可以把实验口径定为：**比较纯 MediaPipe 与 YOLO + MediaPipe 外部桥接链路在离线视频/摄像头输入下的检测稳定性、动态事件触发与交互延迟差异。**

### 2.2 已有 Unity 外部桥接入口

当前 Unity 侧已支持：

- `ExternalVisionFrame.timestamp`
- `UdpGestureReceiver` 接收并队列化 UDP packet
- `ExternalGestureBridgeProvider` 将外部帧转换为 `GestureFrame` / `GestureCommand`
- `ExternalMotionGestureRecognizer` 基于外部 landmark 序列识别 swipe / snap / body shift 等动态事件
- `DebugHud` 显示桥接源、UDP 状态、Pose 点数、动态事件

这说明性能统计可以直接围绕外部帧从 “Python 发出” 到 “Unity 收到/识别/转命令/玩法消费” 的链路展开。

## 3. 风险一：YOLO 实验证据补全方案

### 3.1 论文中建议采用的实验口径

不建议写成“训练了完整 YOLO 手势分类模型”。当前更稳妥、也与项目事实一致的口径是：

> 本文在外部视觉桥接链路中引入 YOLO 检测作为前置定位模块，并与 MediaPipe 关键点提取结合，比较纯 MediaPipe 与 YOLO + MediaPipe 两种输入链路在离线视频与 Unity 交互场景中的稳定性、识别连续性和实时性能。

这样既呼应任务书的 YOLO + MediaPipe 方向，又不要求短期完成大规模训练。

### 3.2 最小可落地实验

#### 实验 A：纯 MediaPipe vs YOLO + MediaPipe 离线回放对比

输入：`bridge/samples/ipn_real/` 下已抽取的 IPN 视频，或从 `训练集/` 中再抽 4～8 个短视频。

对比命令：

```bash
python bridge/start_offline_gesture_test.py --video <video> --once --no-preview
```

```bash
python bridge/start_offline_gesture_test.py --video <video> --once --no-preview --enable-yolo --yolo-model yolo11n.pt --yolo-conf 0.25
```

建议记录指标：

| 指标 | 含义 | 论文用途 |
|---|---|---|
| video_name | 视频名称 | 实验样本索引 |
| mode | MediaPipe / YOLO+MediaPipe | 对比变量 |
| frame_count | 处理帧数 | 样本规模 |
| hand_present_frames | 检出手的帧数 | 检测连续性 |
| hand_present_ratio | hand_present_frames / frame_count | 鲁棒性证据 |
| avg_confidence | 平均手势置信度 | 检测质量参考 |
| dynamic_event_count | Unity 侧动态事件数量 | 游戏交互有效性 |
| swipe_count / snap_count | 分动作统计 | 动作识别分析 |
| avg_packet_interval_ms | UDP 包平均间隔 | 实时性 |

#### 实验 B：Unity 交互链路截图/日志验证

步骤：

1. Unity 切到 `ExternalBridge`。
2. 启动纯 MediaPipe 离线回放。
3. 截图 HUD：桥接源、UDP 状态、动态事件。
4. 启动 YOLO + MediaPipe 离线回放。
5. 截图 HUD：桥接源应显示 `yoloMediapipeBridge | offline:<video>`。
6. 导出 Unity 性能 CSV。

论文用途：证明 YOLO 前置检测不是只存在于 Python 脚本，而是进入了 Unity 外部桥接链路并被游戏系统消费。

### 3.3 建议新增/修改的工程项

#### Python bridge 侧

新增文件：

- `bridge/offline_yolo_mediapipe_benchmark.py`

功能：

- 批量遍历 `bridge/samples/ipn_real/*.mp4` 或指定视频列表。
- 对每个视频分别运行纯 MediaPipe 与 YOLO + MediaPipe。
- 不需要启动 Unity 时，也能统计 Python 侧：帧数、手检出率、平均置信度、平均处理耗时、平均 FPS。
- 输出：默认写入 `bridge/outputs/yolo_mediapipe_benchmark.csv`，也可通过 `--output` 指定到 `Docs/ExperimentResults/`。

也可以先不新增独立脚本，而是在 `mediapipe_udp_bridge.py` 增加：

- `--metrics-output <csv>`
- `--max-frames <n>`
- 结束时写出本次回放统计。

更推荐独立脚本，避免影响当前稳定桥接脚本。

#### Unity 侧

新增文件：

- `Assets/Scripts/Diagnostics/GesturePerformanceMonitor.cs`
- `Assets/Tests/PlayMode/GesturePerformanceMonitorTests.cs`

职责：

- 读取 `GestureInputRouter` 当前输入模式。
- 读取 `ExternalGestureBridgeProvider.CurrentFrame.timestamp`。
- 统计 Unity 当前 FPS、帧时间、UDP 外部帧到达间隔、外部 timestamp 到 Unity 当前时间的估算延迟。
- 统计 `GestureCommand` 触发次数与动态命令次数。
- 支持导出 CSV。

> 注意：Python `time.time()` 是 Unix 秒，Unity `Time.time` 是运行秒，不能直接相减。需要用“首个外部 timestamp 与 Unity 接收时间建立基准偏移”的方式估算链路延迟。

## 4. 风险二：性能指标补全方案

### 4.1 论文中需要的指标

建议不要只写 FPS。论文第 6 章至少补以下四类指标：

| 指标类别 | 指标 | 采集位置 |
|---|---|---|
| 渲染/运行性能 | average_fps、min_fps、p95_frame_ms | Unity `Update()` |
| 输入吞吐 | external_packet_count、avg_packet_interval_ms | `ExternalGestureBridgeProvider` / 监控器 |
| 链路延迟 | avg_estimated_latency_ms、p95_estimated_latency_ms | 外部 timestamp + Unity 接收时间 |
| 交互有效性 | static_command_count、motion_command_count、recognized_motion_types | `GestureInputRouter.CurrentGestureCommand` |

如果后续有时间做人工标注，再补：

- trigger_success_rate：目标动作触发成功率。
- false_activation_rate：无目标动作时误触率。
- task_completion_time：从开始到完成训练/战斗目标的时间。

### 4.2 Unity 内最小实现设计

新增组件：`GesturePerformanceMonitor`

建议挂载位置：

- 由 `CreatePrototypeScene` 挂到 `PlayerRoot` 或单独 `Diagnostics` GameObject。
- 由 `SpellGuardSceneContext` 暴露引用，`DebugHud` 可选显示摘要。

核心字段：

- `GestureInputRouter inputRouter`
- `ExternalGestureBridgeProvider externalBridge`
- `int sampleWindowSeconds = 60`
- `bool recordOnStart = true`
- `string outputDirectory = "ExperimentResults"`

核心统计：

- `totalFrames`
- `elapsedSeconds`
- `frameMsSamples`
- `externalPacketCount`
- `packetIntervalSamples`
- `estimatedLatencySamples`
- `staticCommandCount`
- `motionCommandCount`
- `Dictionary<MotionGestureType, int> motionCounts`

导出 CSV 建议路径：

- 编辑器内：`unity-spell-guard/ExperimentResults/gesture_performance_<timestamp>.csv`
- 运行包内：`Application.persistentDataPath/ExperimentResults/gesture_performance_<timestamp>.csv`

CSV 表头建议：

```text
session_id,mode,source,elapsed_seconds,total_frames,average_fps,min_fps,average_frame_ms,p95_frame_ms,external_packets,avg_packet_interval_ms,avg_estimated_latency_ms,p95_estimated_latency_ms,static_commands,motion_commands,swipe_lr,swipe_rl,snap,point_to_fist,body_shift_left,body_shift_right
```

### 4.3 DebugHud 展示建议

在 `DebugHud` 的“识别与调试信息”面板中增加三行即可：

- `性能：FPS xx.x / p95 xx ms`
- `桥接延迟：avg xx ms / p95 xx ms`
- `实验记录：Recording / Saved <path>`

这三行的价值是答辩截图能直接证明系统具备实时统计能力。

### 4.4 菜单项建议

新增 Editor 菜单：

- `Spell Guard/Diagnostics/Start Performance Capture`
- `Spell Guard/Diagnostics/Stop And Export Performance CSV`
- `Spell Guard/Diagnostics/Open Experiment Results Folder`

如果时间紧，可以先只做运行时按键：

- `F8`：开始/停止采集。
- `F9`：导出 CSV。

## 5. 推荐实施顺序

### 阶段 1：先补数据采集骨架（0.5～1 天）

1. 已新增 `Assets/Scripts/Diagnostics/GesturePerformanceMonitor.cs`。
2. 已在 `CreatePrototypeScene` 中自动挂载并绑定 `GestureInputRouter` / `ExternalGestureBridgeProvider`。
3. 已在 `DebugHud` 中显示 FPS、延迟、记录状态。
4. 已支持 CSV 导出。
5. 已新增基础 PlayMode 测试，验证统计器摘要与 CSV 表头。

产出：Unity 侧性能指标闭环成立。

### 阶段 2：补 YOLO/MediaPipe 离线 benchmark（0.5～1 天）

1. 已新增 `bridge/offline_yolo_mediapipe_benchmark.py`。
2. 已支持输入视频列表或视频目录。
3. 已分别跑 `mediapipe` 与 `yolo_mediapipe` 模式。
4. 默认输出 `bridge/outputs/yolo_mediapipe_benchmark.csv`。
5. 文档记录命令与结果表格。

产出：论文可写“YOLO 前置检测对外部视觉链路的实验对比”。

### 阶段 3：跑完整实验并归档（0.5 天）

1. 选择 4～8 个短视频。
2. 跑纯 MediaPipe benchmark。
3. 跑 YOLO + MediaPipe benchmark。
4. Unity 切 ExternalBridge，录一段带 HUD 的运行视频或截图。
5. 导出 Unity 性能 CSV。
6. 将 CSV、截图、命令写入 `Docs/ExperimentResults/README.md`。

产出：论文第 6 章可直接引用。

## 7. 最小完成标准

这两个风险可以认为被论文层面“基本补齐”的标准是：

1. 至少有 1 个 CSV 证明纯 MediaPipe 与 YOLO + MediaPipe 的离线对比。
2. 至少有 1 个 Unity CSV 证明 ExternalBridge 链路下 FPS、包间隔、估算延迟和动态命令统计。
3. 至少有 2 张截图：
   - YOLO + MediaPipe 桥接源进入 Unity HUD。
   - Unity HUD 显示性能与延迟统计。
4. 论文中不再写“空泛的高鲁棒/低延迟”，而是引用上述 CSV 的实际统计值。

## 8. 不建议短期做的内容

- 不建议临时训练完整 YOLO 手势分类模型。
- 不建议把 LSTM / Transformer 时序模型硬塞进当前 Unity 主线。
- 不建议为了论文指标重写输入系统。
- 不建议把所有 IPN 数据集都做完大规模 benchmark；先做小规模、可复现、可截图的实验闭环。

短期最重要的是：**用已有桥接链路补实验证据，用 Unity 内采集器补真实运行指标。**
