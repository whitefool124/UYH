# 符印守卫 Unity 项目策划案

## 1. 项目概述

### 1.1 项目名称

符印守卫（Spell Guard）

### 1.2 项目一句话

玩家在第一人称视角下，通过摄像头识别到的手势完成移动、菜单操作与施法，在持续逼近的敌人压力下守住自身与结界。

### 1.3 项目定位

本项目是一个面向毕业设计展示的体感交互游戏原型，核心目标不是完成大体量商业内容，而是验证“视觉识别输出可以被稳定转换为 Unity 内可玩的实时交互命令系统”。

项目同时承担三层任务：

- 作为游戏原型，证明手势可以驱动完整的菜单与战斗闭环
- 作为技术原型，验证 YOLO / MediaPipe 到 Unity 的输入链路可行性
- 作为毕设成果，展示数据、识别、命令解析、玩法映射与测试验证之间的完整关系

### 1.4 当前版本形态

当前 Unity 版本已经具备以下基础闭环：

- 主菜单、设置、教程、训练、战斗、结算六个界面状态
- 第一人称 3D 场景中的敌人逼近与玩家防守
- 指向、握拳、V 手势、张掌等静态手势输入
- Snap、左右挥动、PointToFist 等动态手势输入
- 火焰、冰霜、护盾三种法术
- Mock、NativeMediapipe、ExternalBridge 三种输入源切换
- HUD、摄像头预览、动态反馈牌、命令历史等调试展示能力

因此，本项目策划案以“当前可运行版本”为基线，同时为后续扩展预留方向。

## 2. 核心设计目标

本项目的核心设计目标如下：

1. 让玩家明显感觉自己是在“施法”，而不是在做抽象测试动作
2. 让手势交互从菜单到战斗形成完整闭环，而不是只在战斗阶段出现
3. 让识别系统输出的结果可解释、可复现、可调试，适合毕业设计答辩展示
4. 在保证可玩性的前提下，尽量减少手势数量，提升识别稳定性与首次上手成功率
5. 为后续组合技、双手输入、离线回放验证等扩展保留架构空间

## 3. 目标用户与展示场景

### 3.1 目标用户

- 毕设评审教师
- 对体感交互、计算机视觉、人机交互感兴趣的观众
- 首次体验手势游戏的非专业玩家

### 3.2 主要展示场景

- 毕业设计答辩现场演示
- 项目中期汇报或成果展示
- 课程项目或实验室原型展示

### 3.3 体验要求

由于项目主要服务于展示场景，因此应满足：

- 2 到 5 分钟内能完成一轮有效展示
- 旁观者能快速理解输入方式与玩法反馈
- 出现识别误差时，调试信息足够直观，便于解释问题来源

## 4. 世界观与题材包装

项目采用“结印施法防守”的轻幻想包装。

玩家扮演守卫结界的施法者，在敌人持续逼近时，以不同手势完成结印并释放法术。这个包装的作用不是构建复杂叙事，而是为手势输入提供天然语义：

- 指向对应“引导能量”和“锁定方向”
- 握拳对应“攻击性法术蓄放”
- V 手势对应“控制与冻结”
- 张掌对应“防御与结界展开”
- Snap 与挥动类动作对应“快速触发型动态施法”

这种表达方式能够提升动作与结果之间的直觉一致性，使项目更像游戏，而不是视觉识别演示工具。

## 5. 核心体验

玩家在摄像头前伸手进入系统后，可以不依赖鼠标键盘完成主要操作：

1. 通过指向手势在菜单中选中功能项
2. 通过停留确认进入设置、教程、训练或正式战斗
3. 在第一人称场景中用指向手势完成转向与前进
4. 根据敌人距离和威胁，做出火焰印、冰霜印或护盾印完成防守
5. 在更快的输入需求下，通过动态手势直接触发法术
6. 在生命耗尽后进入结算界面，并继续完成再次开始或返回菜单

整体体验强调两个关键词：

- 沉浸感：玩家感觉自己在操控法术
- 可解释性：系统每一步识别与映射都能被看见和说明

## 6. 玩法循环

### 6.1 局外循环

玩家进入游戏后，首先处于菜单状态，可选择：

- 开始战斗
- 进入设置
- 查看教程
- 进入训练

设置页允许调整施法确认时长与敌人节奏难度，教程页用于说明操作方式，训练页用于在低压力环境下熟悉手势输入。

### 6.2 局内循环

正式战斗中的核心循环如下：

1. 玩家进入第一人称场景
2. 敌人从玩家前方扇形区域持续生成并向玩家逼近
3. 玩家使用指向手势完成视角调整，并在需要时前进
4. 玩家识别当前威胁，选择合适法术
5. 玩家通过静态或动态手势完成施法
6. 命中敌人则清除或控制目标，失误则承受伤害
7. 护盾可提供一次防御容错
8. 生命值归零后进入结算状态

### 6.3 展示循环

为了适应答辩展示，推荐实际演示循环为：

1. 先展示菜单与手势控制
2. 进入训练页演示静态手势和动态手势反馈
3. 进入正式战斗，展示移动、施法、敌人逼近与生命系统
4. 展示结算页与重开流程
5. 切换输入模式，说明 Mock / Native / External 的差异

## 7. 输入与交互设计

## 7.1 输入系统定位

本项目的输入系统不是直接把视觉识别结果硬编码到玩法上，而是采用“输入源 -> 手势帧 -> 命令 -> 玩法消费”的分层设计。这样做的原因是：

- 便于切换不同识别来源
- 便于引入动态动作与组合动作
- 便于回放、测试和调试
- 便于在论文中讲清楚系统结构

### 7.2 当前输入源

当前项目支持三种输入源：

1. Mock
2. NativeMediapipe
3. ExternalBridge

三者分别对应：

- 开发调试时的稳定伪输入
- Unity 内原生手势运行路径
- 外部桥接输入路径，用于结合 Python、MediaPipe、UDP 回放等实验能力

### 7.3 当前静态手势

当前版本的主要静态手势如下：

| 手势 | 作用 | 当前用途 |
|---|---|---|
| Point | 指向 | 菜单焦点、视角控制、前进 |
| Fist | 握拳 | 火焰术 |
| VSign | V 手势 | 冰霜术 |
| OpenPalm | 张掌 | 护盾术、部分返回逻辑 |

### 7.4 当前动态手势

当前版本已经具备动态动作识别能力，主要包括：

| 动态手势 | 当前用途 |
|---|---|
| Snap | 快速释放火焰术 |
| PointToFist | 火焰术快速触发 |
| SwipeLeftToRight | 冰霜术或设置切换 |
| SwipeRightToLeft | 护盾术或返回菜单 |
| OpenPalmSlapLeftToRight | 冰霜类动态输入 |
| OpenPalmSlapRightToLeft | 护盾类动态输入 |

### 7.5 菜单交互规则

菜单相关操作以“指向 + 停留确认”为核心：

- 玩家做出 Point 手势时，系统根据手在屏幕中的位置确定焦点区域
- 停留达到阈值后触发页面切换或按钮激活
- 非主菜单页面可通过张掌停留或特定动态动作快速返回
- 设置页可通过左右挥动快速轮换参数

### 7.6 战斗交互规则

战斗中交互分为两类：

- 持续型控制：Point 手势负责转向与前进
- 离散型施法：Fist / V / OpenPalm 或动态动作触发法术

这种分离方式的优点是：

- 保持战斗中的动作语义清晰
- 避免单一手势承担过多功能
- 有利于后续扩展成组合技系统

## 8. 战斗系统设计

### 8.1 战斗视角

当前项目采用第一人称视角。第一人称的选择有三点价值：

- 施法代入感更强
- 更能体现“手势驱动角色”的沉浸感
- 有助于把输入表现、敌人威胁和命中反馈集中在玩家视野前方

### 8.2 玩家状态

玩家当前核心状态包括：

- 生命值
- 护盾状态
- 当前手势识别结果
- 当前待确认法术与确认进度
- 最后成功释放的法术

### 8.3 法术系统

当前法术系统由三种基础法术构成：

#### 火焰术

- 触发方式：握拳、Snap、PointToFist
- 作用：对正前方目标造成伤害
- 定位：主输出、快速处理逼近敌人

#### 冰霜术

- 触发方式：V 手势、左到右挥动类动作
- 作用：冻结敌人一段时间
- 定位：控制、争取反应空间

#### 护盾术

- 触发方式：张掌、右到左挥动类动作
- 作用：为玩家开启持续一段时间的护盾
- 定位：容错、防止连续失误导致瞬间失败

### 8.4 施法确认机制

为降低误识别影响，静态手势施法采用确认时长机制：

- 系统先识别待释放法术
- 玩家持续保持手势一段时间
- 达到阈值后法术正式释放

这一机制的主要作用是：

- 降低抖动和误检带来的误施法
- 让施法过程更像“蓄力”
- 使项目更适合现场展示与讲解

动态手势则跳过长时间蓄力，以突出“快速施法”的价值。

### 8.5 敌人系统

当前版本的敌人属于轻量通用敌人：

- 从玩家前方区域生成
- 持续向玩家移动
- 进入攻击距离后对玩家造成伤害并消失
- 可被火焰清除，也可被冰霜冻结延缓推进

当前敌人尚未做复杂类型区分，但作为毕设原型已足够支撑“输入 -> 反馈 -> 生存压力”的核心闭环。

### 8.6 失败条件

当玩家生命值归零后，战斗结束并进入结算页。

## 9. 界面与流程设计

### 9.1 界面状态

当前项目包含如下界面状态：

- Menu
- Settings
- Tutorial
- Training
- Playing
- Results

这说明项目已经不是单一战斗测试场景，而是具有完整入口与退出逻辑的演示原型。

### 9.2 设置页

设置页当前承载两个核心参数：

- 施法确认时长
- 敌人节奏难度

这是一个非常合理的 MVP 设计，因为它同时关联：

- 输入稳定性
- 战斗压力节奏

也方便在答辩时解释“参数如何影响体验”。

### 9.3 教程页

教程页的作用不是堆文本说明，而是帮助首次体验者理解：

- 如何进入交互状态
- Point 如何控制菜单与视角
- Fist / V / OpenPalm 分别对应什么法术
- 动态手势在什么情况下更高效

### 9.4 训练页

训练页是整个项目非常关键的展示组成部分，因为它将“输入识别验证”和“战斗表现”分隔开来。

训练页的价值包括：

- 降低初次上手门槛
- 便于单独展示识别效果
- 便于调试或演示动态手势反馈
- 为正式战斗前建立玩家信心

### 9.5 结算页

结算页用于承接失败后的反馈与再次体验，引导玩家完成：

- 查看结果
- 返回菜单
- 重新开始

## 10. 反馈设计

### 10.1 识别反馈

项目当前非常强调识别反馈可视化，主要体现在：

- HUD 显示当前手势、置信度、输入来源、动态状态
- 摄像头预览展示当前识别画面
- 动态反馈牌用于提示 Snap 等动作是否已被系统捕获
- 施法器状态文本显示“等待手势”“确认中”“已释放”等过程状态

这些反馈既服务玩家体验，也服务答辩解释与开发调试。

### 10.2 战斗反馈

当前战斗反馈主要来自：

- 法术释放后的状态提示
- 敌人被冻结或被消灭的行为变化
- 玩家生命与护盾变化
- 游戏结束后的状态切换

后续可以继续强化法术粒子、音效和击中反馈，但现阶段的闭环已经成立。

### 10.3 系统反馈

系统级反馈包括：

- 输入模式切换
- 摄像头状态
- 原生识别状态
- 桥接状态
- UDP 状态
- 当前动态事件标签

这部分是本项目区别于普通小游戏原型的重要特征，因为它承担了“研究型展示”的说明职责。

## 11. 技术与玩法的对应关系

本项目的策划价值不只在玩法本身，更在于玩法与技术结构是一一对应的。

### 11.1 视觉识别层

- YOLO / MediaPipe 提供手部或姿态相关输入基础
- Native 与 External 两条输入路径便于比较与验证

### 11.2 运行时抽象层

- GestureFrame 统一不同来源的输入格式
- TrackedHandState 描述手部状态
- GestureCommand 与 GestureCommandHistory 支撑动态命令与短序列识别

### 11.3 玩法映射层

- FpsGestureMotor 消费主手帧实现移动与转向
- GestureSpellCaster 消费静态与动态命令完成施法
- FlowController 消费手势与动作完成菜单流程控制

### 11.4 验证与展示层

- DebugHud 展示识别与运行时状态
- MotionGestureFeedbackBoard 展示动态事件
- PlayMode / EditMode 测试保证当前实现可持续扩展
- 训练数据结构校验增强毕设自检可信度

这使得项目在写作和答辩中具备很强的结构化表达优势。

## 12. 当前版本亮点

从毕设展示角度看，当前 Unity 版本有以下亮点：

1. 不只是识别手势，而是把手势转成 Unity 可消费的实时命令系统
2. 不只是单场景战斗，而是包含菜单、设置、训练、战斗、结算的完整闭环
3. 不只是静态手势，而是已经具备动态手势与命令历史能力
4. 不只是本地即时识别，还支持外部桥接与离线回放验证思路
5. 不只是主观体验演示，还有数据结构校验和自动化测试支撑

## 13. 当前问题与风险

### 13.1 玩法层风险

- 当前敌人类型较单一，策略深度仍有限
- 第一人称场景中，玩家需要兼顾移动、瞄准和施法，学习成本高于纯平面原型

### 13.2 识别层风险

- 光照、镜头角度、手型差异会影响识别稳定性
- 动态手势阈值在不同玩家之间可能需要重新调节

### 13.3 展示层风险

- 如果现场设备性能、摄像头质量或环境光变化较大，原生识别体验可能波动
- 若缺少明确演示顺序，评审可能先注意到调试信息而不是玩法价值

## 14. 后续扩展方向

在不推翻当前架构的前提下，后续优先级建议如下：

### 14.1 高优先级

- 为敌人增加轻量类型差异，建立更明显的法术克制关系
- 增强法术视觉反馈与命中反馈
- 优化教程与训练页引导，提高首次上手成功率
- 进一步稳定 Native / External 两条输入链路

### 14.2 中优先级

- 增加组合技与短序列触发
- 增加双手输入能力
- 引入更多可回放数据样例，形成更正式的验证集

### 14.3 低优先级

- 丰富世界观包装与 UI 美术
- 扩展成长系统、波次设计、Boss 或更多关卡内容

## 15. 毕设价值总结

《符印守卫》Unity 项目的价值不在于堆砌复杂内容，而在于它用一个可运行、可展示、可调试、可验证的 3D 交互原型，证明了以下命题：

1. 手势识别可以从视觉结果提升为可复用的游戏命令层
2. 体感输入可以驱动 Unity 中完整的菜单与战斗流程
3. 动态手势、外部桥接、离线回放和测试验证可以共同组成较完整的毕业设计技术链路
4. 游戏化包装能够显著提升手势识别课题的展示效果与表达完整性

因此，本项目既是一个面向展示的体感施法游戏原型，也是一个结构清晰、论证路径明确的毕业设计实现载体。
