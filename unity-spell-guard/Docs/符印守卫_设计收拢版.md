# 符印守卫 设计收拢版

## 一、当前版本核心定位

《符印守卫》当前版本的目标，不是做一个自由第一人称体感动作游戏，而是做一个：

**全手势操作、节点地图推进、房间制战斗、适合毕业设计展示的游戏原型。**

核心要求只有三条：

1. 全流程只用手势完成
2. 输入更像手柄，不像鼠标
3. 地图、移动、战斗三者必须互相支持

## 二、输入哲学

当前方案已经明确：

- 少依赖 `Point`
- 少依赖屏幕坐标和光标思路
- 多依赖离散动作和明确语义

也就是说，输入要从“指哪里”变成“做什么”。

## 三、最终主手势方案

当前推荐的主手势收束为：

- 握拳：火焰术
- V 手势：冰霜术
- 张掌：护盾术
- 向左挥：左切换 / 左闪
- 向右挥：右切换 / 右闪
- 握拳保持：确认
- 张掌保持：返回
- 打响指：快速火焰术

条件成熟后再补：

- 向前推：前冲 / 推进
- 防御姿态：停步 / 稳定站位

高阶扩展层可做：

- 两段或三段静态组合手势

## 四、交互方案

### 系统交互

- 向左挥：前一个选项
- 向右挥：后一个选项
- 握拳保持：确认
- 张掌保持：返回

### 地图交互

- 向左挥：选择左侧节点 / 上一节点
- 向右挥：选择右侧节点 / 下一节点
- 握拳保持：进入当前节点
- 张掌保持：退出地图层

### 战斗交互

- 握拳：火焰术
- V 手势：冰霜术
- 张掌：护盾术
- 向左挥：左闪
- 向右挥：右闪
- 打响指：快速火焰术

## 五、交互状态机

当前建议采用五态主状态机：

- `SystemUI`
- `MapChoice`
- `Training`
- `Playing`
- `Results`

主链路为：

`SystemUI -> MapChoice -> Playing -> MapChoice -> ... -> Results -> SystemUI`

训练支链为：

`SystemUI -> Training -> SystemUI`

这套状态机的目的，是确保：

- 同一时间只处理一种主要输入意图
- 菜单、地图、训练、战斗之间不会互相串扰

## 六、地图方案

地图不做开放大地图，而做：

**节点地图 + 房间推进**

当前推荐结构：

- 每幕 5 到 7 个节点
- 每层最多 2 个可选节点
- 当前层只做一次选择
- 完成房间后自动推进到下一层

固定节点类型为：

- 起点节点
- 普通战斗节点
- 精英战斗节点
- 事件节点
- 休整节点
- Boss 节点

## 七、房间模板

当前版本只做四类房间模板：

1. 直线推进房
2. 环形防守房
3. 双压迫走廊房
4. 精英 / Boss 房

每个房间都必须满足：

- 有明确目标
- 有明确站位意义
- 有更优法术选择
- 有更优移动方式

## 八、三关结构

### 第一关：教学关

重点：

- 菜单切换
- 确认 / 返回
- 三法术基础输入
- 左右闪避

地图：

- 单一路线
- 低压房间
- 直线推进为主

### 第二关：策略关

重点：

- 节点切换
- 路线选择
- 移动与控场配合

地图：

- 双路线节点图
- 环形房 + 走廊房混合

### 第三关：高潮关

重点：

- 高压闪避
- 快速火焰输入
- 最终目标确认

地图：

- 精英 / Boss 房
- 多波威胁
- 强化位置判断和法术切换

## 九、范围控制

当前明确不做：

- 开放大地图
- 自由 3D 光标导航
- 复杂迷宫
- 超过 4 类房间模板
- 超过 2 层的节点分支树
- 高自由度第一人称精确瞄准
- 商店 / 背包 / 货币 / 构筑系统

## 十、当前最终结论

《符印守卫》当前版本应收束为：

- 输入：离散动作式手势输入
- 地图：节点地图
- 战斗：房间推进
- 交互：左右切换 + 确认 + 返回
- 移动：左右闪避 + 可选前冲
- 法术：火 / 冰 / 盾 + 快速火焰

这套方案的价值在于：

1. 全流程仍然只用手势完成
2. 玩法比原来的施法 demo 更完整
3. 地图和移动真正成为决策空间
4. 范围仍然可控，适合毕业设计落地
