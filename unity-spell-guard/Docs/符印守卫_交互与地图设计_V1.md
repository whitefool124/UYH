# 符印守卫 交互与地图设计 V1

## 一、文档目标

这份文档用于在现有策划、输入方案、动作表和手势规范的基础上，收敛《符印守卫》的交互与地图设计方案。

目标不是继续发散概念，而是回答三个落地问题：

1. 玩家如何只靠手势完成完整交互闭环
2. 地图结构如何服务当前输入方案，而不是反过来拖垮输入系统
3. 哪种关卡与房间结构最适合毕业设计原型的范围控制和展示效果

## 二、五轮审查结论

这版方案经过五轮自审收束，五轮关注点如下：

### 第一轮：输入兼容性审查

结论：交互必须服从当前“类手柄式离散动作”方案，不能再依赖 `Point + cursor` 作为主交互轴。

因此：

- 菜单改为焦点切换式
- 地图改为节点切换式
- 战斗移动改为闪避 / 前冲 / 停步式
- 房间和镜头都要降低对精细瞄准的依赖

### 第二轮：范围控制审查

结论：不做开放地图，不做自由 3D 漫游，不做复杂迷宫。

当前最稳的结构是：

- 节点地图
- 房间式推进
- 少量模板房间复用

### 第三轮：展示可读性审查

结论：地图和交互必须让旁观者一眼看懂。

因此：

- 菜单动作要少
- 节点高亮要明显
- 房间目标要单一
- 玩家行为要能被旁观者快速理解为“切换、确认、闪避、施法、推进”

### 第四轮：玩法成立性审查

结论：地图不能只是背景，必须给移动和施法建立明确的决策关系。

因此：

- 不同房间要让不同法术更有价值
- 不同房间要让左右闪避和站位选择有意义
- 不同节点要让路线选择有收益与代价差异

### 第五轮：实现路径审查

结论：当前最合理的实现顺序是：

1. 系统交互改造
2. 节点地图交互
3. 房间模板搭建
4. 移动与敌人空间关系校准
5. 结算与重开闭环

## 三、最终交互哲学

《符印守卫》的交互要做到：

- 玩家在任何时刻只处理一种主要输入意图
- 每个动作都有明确反馈
- 交互更像控制器，不像空中鼠标

因此，所有交互统一分为四类：

1. 系统交互
2. 地图交互
3. 移动交互
4. 战斗交互

## 四、系统交互设计

## 4.1 主菜单交互

主菜单建议采用单焦点横向或纵向切换结构。

### 推荐菜单项

- 开始游戏
- 训练场
- 设置
- 教程

### 推荐交互映射

- 向左挥：切换到前一个菜单项
- 向右挥：切换到后一个菜单项
- 握拳保持：确认当前菜单项
- 张掌保持：返回或取消

### 设计理由

- 不依赖 Point
- 摄像头位置变化对体验影响更小
- 观众容易理解“左切 / 右切 / 确认 / 返回”

## 4.2 设置页交互

设置页不做复杂滑杆，采用焦点项切换 + 离散值轮换。

### 推荐设置项

- 手势确认时长
- 敌人节奏难度
- 音量开关（可选）

### 推荐交互映射

- 向左挥 / 向右挥：切换当前条目的值
- 握拳保持：确认当前变更
- 张掌保持：返回上一级

### 设计理由

- 不需要自由光标
- 适合原型阶段
- 程序逻辑简单

## 4.3 教程页与训练页交互

教程页和训练页应承担不同职责。

### 教程页

作用：

- 解释核心规则
- 展示手势语义
- 说明地图和房间目标

交互：

- 向左挥 / 向右挥：翻页或切换说明项
- 握拳保持：进入训练或开始战斗
- 张掌保持：返回菜单

### 训练页

作用：

- 分离“识别验证”和“正式战斗”
- 让玩家体验三法术、闪避和快速火焰

交互：

- 战斗动作全部有效
- 张掌保持：退出训练返回菜单

## 五、地图交互设计

## 5.1 为什么用节点地图

节点地图有四个优势：

1. 适合手势式焦点切换
2. 容易展示路线选择
3. 容易控制开发规模
4. 适合房间模板复用

## 5.2 节点地图结构

建议每关采用“小节点图”而不是大地图。

### 单关结构建议

- 起点节点
- 2 到 3 个中间节点
- 1 个分支选择
- 1 个高潮节点
- 1 个出口 / Boss 节点

### 节点类型建议

- 普通战斗房
- 精英战斗房
- 恢复房
- 事件房
- 试炼房
- Boss 房

## 5.3 节点地图交互映射

- 向左挥：高亮左侧节点或上一节点
- 向右挥：高亮右侧节点或下一节点
- 握拳保持：进入当前节点
- 张掌保持：返回上一层地图或退出选路

### 设计原则

- 地图上同一时刻只有一个高亮焦点
- 高亮路径必须可视化
- 不做自由拖拽和自由定位

### 节点地图原型约束

为确保地图设计不失控，节点地图原型进一步收束为：

- 每幕 5 到 7 个房间节点
- 每层最多 2 个可选节点
- 玩家只在当前层做选择，完成房间后自动推进到下一层
- 不做全图自由浏览，不做回退重走，不做复杂分支树

### 推荐节点类型固定为 6 类

- 起点节点
- 普通战斗节点
- 精英战斗节点
- 事件节点
- 休整节点
- Boss 节点

### 节点地图节奏建议

#### 第一幕

- 起点
- 普通战斗
- 事件 / 休整（二选一）
- 普通战斗 / 精英（二选一）
- Boss

#### 第二幕

- 起点
- 普通战斗 / 事件
- 休整 / 精英
- 普通战斗
- 事件 / 普通战斗
- Boss

#### 第三幕

- 起点
- 普通战斗 / 精英
- 事件
- 休整 / 普通战斗
- 精英 / 事件
- 普通战斗
- Final Boss

### 节点地图反失控规则

- 不做商店
- 不做背包 / 货币 / 构筑系统
- 不做隐藏房和复杂钥匙门
- 不做超过 2 个选项的分支层
- 不为地图单独新增手势

## 六、房间地图设计

## 6.1 房间地图总原则

房间是战斗和移动成立的最小单位。

每个房间必须同时满足：

- 有明确目标
- 有明确站位意义
- 有至少一种更优法术选择
- 有至少一种更优移动方式

## 6.2 推荐房间模板

当前版本建议先只做四类模板房间。

### 模板 A：直线推进房

特点：

- 入口到出口清晰
- 适合教学
- 适合展示前进与基础施法

适合目标：

- 到达出口
- 清掉阻挡敌人

适合展示：

- 握拳主输出
- 张掌保命推进

### 模板 B：环形防守房

特点：

- 中心有保护点或安全点
- 敌人从外围出现
- 玩家需要闪避和换位

适合目标：

- 守住结界 20 秒
- 清掉三波敌人

适合展示：

- 左右闪避
- 冰霜术控场
- 护盾术容错

### 模板 C：双压迫走廊房

特点：

- 左右两侧或前后交替来敌
- 空间狭窄
- 强化路线和位置判断

适合目标：

- 通过危险走廊
- 在有限受击次数内突破

适合展示：

- 火焰术开路
- 护盾穿越
- 闪避重置站位

### 模板 D：精英 / Boss 房

特点：

- 单一高压目标 + 少量伴生威胁
- 空间干净但压力集中
- 适合展示高阶输入与节奏判断

适合目标：

- 破防精英
- 完成最终守卫

适合展示：

- 三法术关系
- 打响指快速火焰
- 组合手势作为后期可选大招

## 七、交互与地图的联动关系

## 7.1 菜单要服务地图

菜单不是单独系统，它必须把玩家引导到地图与房间循环里。

所以菜单结构要短、路径要短，最好在 2 次确认内进入训练或正式关卡。

## 7.2 地图要服务移动

如果地图只是切节点、房间里又不用动，那地图就没有意义。

因此每个房间都至少要让玩家回答一个问题：

- 我该不该换位
- 我该不该推进
- 我该不该留在原地

## 7.3 移动要服务战斗

移动系统不是展示动作，而是让战斗决策成立。

因此：

- 闪避必须能躲掉真实威胁
- 前冲必须能带来位置收益
- 停步必须能带来判断收益

## 7.4 战斗要服务关卡目标

每个房间不只是“刷怪”，而是服务当前节点目标，例如：

- 守住
- 突破
- 到达
- 激活
- 终结

## 八、三关对应的交互与地图安排

## 8.1 第一关：教学关

### 交互重点

- 左右切换菜单
- 确认 / 返回
- 三法术基础输入
- 左右闪避

### 地图重点

- 直线推进房
- 单一路线
- 低压遭遇房

### 目标

让玩家和观众都理解：
“这是一个只用手势就能完整操作的游戏。”

## 8.2 第二关：策略关

### 交互重点

- 节点切换
- 路线选择
- 移动与控场配合

### 地图重点

- 双路线节点图
- 环形房 + 走廊房混合
- 敌人差异更明显

### 目标

让玩家和观众理解：
“地图和移动让手势输入变成了战斗决策，而不是简单施法。”

## 8.3 第三关：高潮关

### 交互重点

- 高压闪避
- 快速火焰输入
- 最终目标确认

### 地图重点

- 精英 / Boss 房
- 多波威胁
- 需要位置判断和技能切换

### 目标

让玩家和观众理解：
“这不是 demo，而是一个完整、可展示、可答辩的手势游戏原型。”

## 九、范围控制规则

为了确保落地，当前交互与地图设计必须遵守以下限制：

### 不做

- 开放大地图
- 自由 3D 光标导航
- 复杂迷宫
- 超过 4 类房间模板
- 超过 2 层的节点分支树
- 高自由度第一人称精确瞄准

### 当前建议只做

- 3 个关卡
- 4 类房间模板
- 1 套节点地图逻辑
- 1 套统一系统交互逻辑
- 1 套统一战斗交互逻辑

## 十、交互状态机详细版

为避免菜单、地图、训练、战斗之间的输入串扰，当前版本建议采用五态主状态机：

- `SystemUI`
- `MapChoice`
- `Training`
- `Playing`
- `Results`

### 10.1 `SystemUI`

覆盖页面：

- 主菜单
- 设置
- 教程
- 章节选择等非战斗页面

允许动作：

- 向左挥：前一项
- 向右挥：后一项
- 握拳保持：确认
- 张掌保持：返回

禁止动作：

- 全部施法动作
- 全部战斗移动动作
- 自由光标命中

### 10.2 `MapChoice`

覆盖页面：

- 节点地图
- 路线分支
- 事件节点选择

允许动作：

- 向左挥：高亮左节点 / 上一节点
- 向右挥：高亮右节点 / 下一节点
- 握拳保持：进入当前节点
- 张掌保持：退出地图层或返回上一级

禁止动作：

- 全部施法动作
- 全部战斗移动动作
- 自由地图光标

### 10.3 `Training`

定位：

- 识别验证
- 基础教学
- 安全练习

允许动作：

- 三法术
- 左右闪避
- 打响指快速火焰
- 可选前冲
- 张掌保持退出训练

特例：

- 训练状态是唯一允许“战斗输入 + 系统退出”共存的场景
- 必须通过状态优先级明确：退出 > 高阶动作 > 普通施法 > 移动

### 10.4 `Playing`

定位：

- 正式房间战斗
- 房间推进

允许动作：

- 左闪
- 右闪
- 可选前冲
- 停步 / 防御姿态
- 火焰术
- 冰霜术
- 护盾术
- 快速火焰

禁止动作：

- 菜单切换
- 地图切换
- 系统返回直跳菜单
- Point 驱动主视角

### 10.5 `Results`

定位：

- 战斗结算
- 关卡完成
- 失败重开

允许动作：

- 向左挥 / 向右挥切换选项
- 握拳保持确认
- 张掌保持返回

禁止动作：

- 全部施法动作
- 全部战斗移动动作

### 10.6 推荐主链路

正式流程主链路为：

`SystemUI -> MapChoice -> Playing -> MapChoice -> ... -> Results -> SystemUI`

训练支链为：

`SystemUI -> Training -> SystemUI`

或：

`SystemUI -> Training -> Playing / MapChoice`

## 十一、最终收束结论

《符印守卫》的交互与地图设计，最终应收束为：

### 交互侧

- 系统层：左右切换 + 确认 + 返回
- 地图层：节点切换 + 路线确认
- 移动层：左右闪避 + 可选前冲 + 停步
- 战斗层：三法术 + 快速火焰

### 地图侧

- 节点地图
- 房间推进
- 四类模板房间
- 三关结构

### 核心价值

这套方案能保证：

1. 全流程仍然只用手势完成
2. 地图和移动不是装饰，而是实际决策空间
3. 输入方案和地图结构互相适配
4. 范围可控，适合毕业设计原型落地

如果按这条路线推进，项目就会从“能用手势施法的原型”真正升级为“具有清晰关卡、地图和交互逻辑的手势游戏”。
