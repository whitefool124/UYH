# 符印守卫 手势系统规划框架

## 一、文档目标

这份文档的目标不是继续泛谈“有哪些手势”，而是为《符印守卫》V3 后续实现建立一套可落地的输入规划框架，避免手势系统在功能扩展过程中不断叠加、相互冲突、难以教学和难以调试。

本框架重点解决五个问题：

1. 手势系统如何分层
2. 当前版本应保留哪些核心手势
3. 菜单、导航、施法之间如何避免冲突
4. 输入识别的优先级和状态切换如何定义
5. 玩家应按什么顺序学习这些手势

## 二、设计原则

后续所有手势设计都必须遵守以下原则：

### 2.1 全手势闭环

从主菜单进入、选关、战斗、结算到返回菜单，核心流程全部可以仅通过手势完成。

### 2.2 少而稳优先于多而炫

对毕业设计原型而言，手势的数量不是卖点，稳定性和可解释性才是卖点。

### 2.3 一个手势只承担一个主语义

如果一个动作同时承担菜单确认、移动触发和施法输入，系统会迅速变得难以理解、难以调试、难以教学。

### 2.4 同一时刻只处理一个主要输入意图

系统必须明确玩家当前处于“菜单输入”“导航输入”“战斗施法输入”中的哪一种主状态，避免多层解释同时发生。

### 2.5 动态手势解决高压效率，不解决基础可玩性

静态手势负责新手基础体验，动态手势负责高压场景下的快速反应和高阶表达，不能本末倒置。

## 三、手势系统分层

建议将整个手势系统拆成四层。

### 3.1 系统层手势

用途：

- 主菜单导航
- 选关
- 设置调整
- 教程页切换
- 结算确认
- 返回上一级

要求：

- 动作少
- 易学
- 低误触
- 低疲劳

### 3.2 导航层手势

用途：

- 控制视角
- 缓慢前进
- 短位移
- 停止移动

要求：

- 和施法手势语义清晰分离
- 能在战斗中稳定工作
- 不要求连续大幅度挥舞

### 3.3 战斗层手势

用途：

- 基础法术输入
- 蓄力确认
- 常规战斗循环

要求：

- 差异大
- 易识别
- 适合教学
- 可配合确认机制

### 3.4 高阶层手势

用途：

- 快速施法
- 高压反应
- 组合动作
- 未来双手输入扩展

要求：

- 不是新手必学
- 作为效率层和熟练度层使用
- 单独训练和单独调试

## 四、当前版本手势词典建议

## 4.1 系统层手势词典

| 手势 | 语义 | 用途 | 备注 |
|---|---|---|---|
| Point | 焦点指向 | 菜单选中、选关选点 | 系统层核心手势 |
| Dwell | 停留确认 | 激活按钮、确认节点 | 不是独立手势，而是交互规则 |
| OpenPalm Hold | 返回 / 退出 | 返回上一级、退出子页面 | 稳定且不易误触 |
| SwipeRightToLeft | 快捷返回 | 结果页、设置页快速返回 | 可选高效交互 |

建议：

- 系统层不要继续扩手势数量
- 保持“指向 + 停留确认 + 返回”三件事足够清楚

## 4.2 导航层手势词典

| 手势 | 语义 | 用途 | 备注 |
|---|---|---|---|
| Point | 观察 / 瞄准 | 控制视角 | 导航层核心手势 |
| Point + High Hold | 推进 | 缓慢前进 | 通过手位高度触发，不增加新手势 |
| SwipeLeft | 左闪 | 紧急脱离或换位 | 建议短 CD |
| SwipeRight | 右闪 | 紧急脱离或换位 | 建议短 CD |
| Hand Lost / Neutral | 停止 | 停止移动 | 默认安全状态 |

建议：

- 当前阶段不要做后退和奔跑
- 先把“看”“走”“闪”三种空间动作做清楚

## 4.3 战斗层手势词典

| 手势 | 语义 | 法术 | 定位 |
|---|---|---|---|
| Fist | 攻击性结印 | 火焰术 | 主输出 |
| VSign | 控制性结印 | 冰霜术 | 控场与减压 |
| OpenPalm | 防御性结印 | 护盾术 | 防御与容错 |

建议：

- 三法术方案保持不变
- 静态手势继续作为基础主玩法
- 每个法术都保留确认时间机制

## 4.4 高阶层手势词典

| 手势 | 映射 | 用途 | 定位 |
|---|---|---|---|
| Snap | 快速火焰 | 紧急输出 | 快速响应 |
| PointToFist | 快速火焰确认 | 攻击衔接 | 技巧型输入 |
| SwipeLeftToRight | 快速冰霜 | 紧急控场 | 高压场景 |
| SwipeRightToLeft | 快速护盾 | 紧急保命 | 高压场景 |

建议：

- 当前阶段先只保留这四个动态动作
- 不要过早引入复杂组合技

## 五、手势状态机规划

为了避免识别冲突，建议将输入系统做成状态机，而不是“每一帧都尝试解释一切”。

### 5.1 一级状态

建议当前版本至少有以下一级状态：

1. `SystemUI`
2. `Navigation`
3. `CombatCast`
4. `HighPressureOverride`

### 5.2 一级状态说明

#### SystemUI

生效场景：

- 菜单
- 设置
- 选关
- 结算

解释规则：

- 优先识别 Point
- 其次判断是否停留确认
- 最后判断是否触发返回动作

在此状态下：

- 不解释战斗施法
- 不解释导航推进

#### Navigation

生效场景：

- 玩家可自由移动但未进入施法确认流程

解释规则：

- Point 优先解释为视角控制
- Point 高位保持解释为前进
- 左右短挥解释为闪避

在此状态下：

- 不直接把 Point 当施法
- OpenPalm 默认不直接触发系统返回，而应优先看是否处于战斗环境

#### CombatCast

生效场景：

- 玩家做出稳定的 Fist / VSign / OpenPalm 并进入施法确认期

解释规则：

- 当前候选法术锁定
- 进入确认计时
- 中途切换手势则重置确认
- 手丢失则取消

在此状态下：

- 降低导航解释优先级
- 防止前进和施法同时误触发

#### HighPressureOverride

生效场景：

- 系统检测到有效动态手势

解释规则：

- 动态动作直接映射到高优先级施法或闪避
- 触发后短时间内锁定状态，避免连续抖动重复触发

在此状态下：

- 允许覆盖普通静态确认逻辑
- 但必须有冷却和节流机制

## 六、识别优先级建议

## 6.1 总体优先级

建议当前版本采用如下优先级：

1. 场景状态优先
2. 高阶动态动作优先
3. 系统级返回动作优先
4. 静态施法确认优先
5. 导航输入优先
6. 兜底进入 Neutral

### 6.2 原则说明

#### 场景状态优先于动作本身

同一个 `OpenPalm` 在菜单里可以表示返回，在战斗里应优先解释为护盾术，在结果页则可以解释为返回或确认。因此动作语义必须依赖状态，而不是全局固定。

#### 动态动作优先于静态停留

如果用户做出明确的 `Snap` 或快速挥动，这通常代表更强烈的实时意图，应优先于正在累计的静态确认进度。

#### 没有明确意图时必须回到 Neutral

系统宁可少触发，也不要在模糊状态下强行猜测。

## 七、冲突规则建议

### 7.1 Point 的冲突处理

Point 是最重要也最容易冲突的手势。

冲突来源：

- 菜单里它是焦点选择
- 战斗里它是视角控制
- 某些系统里还可能想拿它做施法起手

处理原则：

- 在 `SystemUI` 中，Point 只能解释为焦点控制
- 在 `Navigation` 中，Point 只能解释为视角控制与推进
- 不允许 Point 同时承担基础施法功能

### 7.2 OpenPalm 的冲突处理

OpenPalm 当前同时可能承担：

- 护盾术
- 返回动作
- 防御姿态

处理原则：

- 菜单与结果页中，OpenPalm 优先解释为返回
- 战斗中，OpenPalm 优先解释为护盾术
- 导航中，如无返回上下文，则只保留短暂停止或防御语义，不做页面退出

### 7.3 Swipe 的冲突处理

Swipe 既可能用于闪避，也可能用于快速施法，还可能用于设置切换。

处理原则：

- 在设置页中，Swipe 用于参数切换
- 在战斗高压场景中，Swipe 映射快速法术或闪避，但同一版本内不要同时承担两种结果

建议当前版本定死：

- 横向短挥：战斗里优先闪避
- 明确识别到高阶动态模式时：才映射成快速法术

也就是说，后续要么分方向，要么分速度阈值，不要模糊混用。

## 八、确认、冷却与节流机制

### 8.1 确认机制

静态施法必须有确认机制：

- 候选识别
- 保持稳定
- 达到阈值
- 触发施法

### 8.2 冷却机制

动态动作必须有冷却窗口，否则高频抖动会导致重复触发。

建议：

- Snap、Swipe、PointToFist 都应有独立 cooldown
- 同类动作之间应有最小间隔

### 8.3 节流机制

菜单确认和返回也应有短节流：

- 防止一次停留导致多次进入
- 防止返回动作连续触发多层页面跳转

## 九、教学顺序规划

手势系统是否成功，不只取决于识别效果，也取决于教学顺序是否正确。

建议按以下顺序教学：

### 9.1 第一步：系统层

先让玩家学会：

- Point 选中
- 停留确认
- OpenPalm 返回

目标：

让玩家理解“这个游戏真的不用键鼠”。

### 9.2 第二步：导航层

再让玩家学会：

- Point 控视角
- 高位 Point 前进
- 左右闪避

目标：

让玩家理解“手势不只是点按钮，还能控制空间移动”。

### 9.3 第三步：战斗层

再引入三种基础法术：

- Fist
- VSign
- OpenPalm

目标：

让玩家建立稳定、低压的基础施法循环。

### 9.4 第四步：高阶层

最后再引入：

- Snap
- PointToFist
- 快速挥动型施法

目标：

让玩家感受到“高阶动作可以更快，但不是必须”。

## 十、当前版本 MVP 建议

为了保证实现节奏，建议手势系统 MVP 固定为：

- 系统层：Point + Dwell + OpenPalm Return
- 导航层：Point Look + High Hold Forward + Left/Right Dodge
- 战斗层：Fist / VSign / OpenPalm
- 高阶层：Snap + PointToFist + 2 个方向型快速动作

不要在当前阶段新增：

- 双手复合施法
- 画符轨迹
- 连续复杂 combo
- 多段长链动态动作

## 十一、后续实现优先级

建议后续按这个顺序推进：

1. 固化手势词典与状态机
2. 实现菜单、导航、施法三层互斥规则
3. 补全动态手势的冷却和节流
4. 做训练关教学顺序验证
5. 做高压场景下的误触测试
6. 再考虑组合技和双手扩展

## 十二、总结

《符印守卫》的手势系统后续不应该继续“加动作”，而应该优先“定边界”。

这套规划框架的价值在于：

- 把系统层、导航层、战斗层、高阶层明确拆开
- 把词典、状态机、优先级和冲突规则固定下来
- 让后续实现、调试、教学和答辩说明都更清晰

只要这个框架立住，后面无论是做关卡、地图、移动还是高阶施法，都会有一个稳定的输入基础，而不会把整个项目重新拖回“手势 demo 拼凑”的状态。
