# 符印守卫 纯手势 UI 交互界面定义

## 1. 目标

当前 P0 要求中，至少需要一个完全由手势驱动的 UI 交互界面达到可稳定演示状态。

这个界面应满足：

- 不依赖键盘和鼠标
- 不依赖手在屏幕上的连续指向定位
- 逻辑简单、路径短、演示明确
- 能让评审一眼理解“这不是战斗内局部手势，而是完整的 UI 输入系统”

## 2. 推荐界面

建议把“开始界面 / 模式选择界面”作为当前版本的纯手势 UI 核心展示界面。

理由：

- 进入游戏后第一眼就能展示
- 演示成本最低
- 不会和战斗输入混在一起
- 非专业评审最容易理解

## 3. 界面结构建议

### 3.1 一级菜单

- 开始试炼
- 教学说明
- 模式说明
- 设置
- 退出 / 返回（如需要）

### 3.2 设计原则

- 菜单项数量少
- 单层尽量不超过 4~5 项
- 每次进入下一层最多两步完成

## 4. 交互方式建议

### 4.1 核心原则

- 不使用基于手位置的“光标指向”方式
- 使用“焦点切换 + 确认”的纯离散输入逻辑

### 4.2 建议交互逻辑

- 左向动态动作：切换到上一个 / 左一个菜单项
- 右向动态动作：切换到下一个 / 右一个菜单项
- 确认手势：进入当前焦点项
- 返回手势：回到上一级或返回主菜单

### 4.3 焦点反馈

- 当前焦点项必须有明显高亮
- 切换时有平滑过渡反馈
- 确认时有短暂充能或激活动画

## 5. 状态流转定义

### 5.1 主菜单状态

- 玩家通过左右切换菜单项
- 通过确认动作进入教学、开始试炼、设置等分支

### 5.2 子界面状态

- 玩家通过同样的切换方式浏览选项
- 通过返回动作回主菜单

### 5.3 战斗前入口状态

- 玩家在开始试炼前看到简短关卡信息或模式确认
- 再通过确认动作进入战斗

## 6. 成功 / 取消 / 返回逻辑

### 6.1 成功

- 进入对应页面或关卡
- 应有明确页面切换反馈

### 6.2 取消

- 当前版本可不单独设计“取消”，统一收敛到“返回”语义

### 6.3 返回

- 从设置页返回主菜单
- 从说明页返回主菜单
- 从结算页返回主菜单

## 7. P0 验收标准

这个纯手势 UI 界面要满足：

1. 玩家不接触键盘鼠标即可完成一次界面选择
2. 可稳定进入教学或开始试炼
3. 可稳定从子页面返回主菜单
4. 评审能看懂切换、确认、返回三种语义

## 8. 当前结论

- 当前 P0 的纯手势 UI 交互界面，建议锁定为“开始界面 / 模式说明 / 教学入口”这条短链路。
- 这条链路应采用“焦点切换 + 确认 + 返回”的离散输入方式。
- 不依赖手在屏幕中的连续位置，是当前最稳妥的全手势 UI 方案。

## 9. 临时实现原则

- 如果纯手势 UI 在短期内存在识别不稳定问题，可先使用键盘 / 鼠标映射相同交互语义进行临时实现。
- 临时方案仅用于开发推进与关卡跑通，不改变最终纯手势 UI 目标。
- 正式演示版本仍需至少保留一个完全由手势驱动的 UI 核心界面。
