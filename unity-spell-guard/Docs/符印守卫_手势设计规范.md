# 符印守卫 手势设计规范

## 一、文档目的

这份文档用于统一《符印守卫》后续所有与手势相关的设计决策，避免项目在玩法扩展过程中出现以下问题：

- 手势越来越多，但语义越来越乱
- 同一个动作在不同系统里承担多个冲突功能
- 输入设计越来越像“体感鼠标”，而不是“游戏控制器”
- 技术实现和策划表达逐渐脱节

本规范的目标不是列出所有可能手势，而是建立一套稳定、可扩展、可解释的手势设计标准。

## 二、核心输入哲学

### 2.0 下一轮开发硬约束（2026-05-12）

下一轮新增手势识别必须遵守以下边界：

- 不做手势定位：不新增依赖手部屏幕坐标、手指指向、光标命中按钮、指向某个区域的玩法输入。
- 不做身体捕捉：不新增依赖 Pose Landmark、身体左移 / 右移、躯干倾斜、站位偏移的玩法输入。
- 不做 Point 主输入：`Point` 不再作为新增菜单、移动、施法或训练步骤的核心输入，只能作为兼容 / 调试 / 过渡说明保留。
- 新增手势只考虑离散动作：握拳保持、张掌保持、左右挥、打响指、短静态结印序列。

这条约束优先级高于旧文档中任何关于 Point 控视角、Point 推进、BodyShift 或身体移动的建议。

### 2.1 从“指哪里”转向“做什么”

《符印守卫》后续的手势输入不应继续以 `Point` 这类空间指向为核心，而应逐步转向“动作语义驱动”。

也就是说，玩家记住的应当是：

- 我做了什么动作
- 这个动作在当前状态下代表什么命令

而不是：

- 我的手现在在屏幕哪个位置
- 我的手指正指向哪里

### 2.2 输入更像手柄，不像鼠标

项目的整体输入设计应更接近：

- 手柄按键
- 动作游戏指令
- 格斗游戏的离散输入

而不是接近：

- 鼠标光标
- 屏幕坐标点选
- 第一人称精确瞄准

### 2.3 离散优先，连续谨慎

视觉手势系统更适合：

- 切换
- 确认
- 返回
- 闪避
- 施法
- 高压快速触发

不适合优先承担：

- 高精度连续瞄准
- 光标移动
- 精细镜头操控

## 三、总设计原则

后续所有手势设计都必须遵守以下原则。

### 3.1 一个手势只定义一个主语义

同一个动作在不同状态下可以有上下文差异，但必须有一个清晰的主语义，不能在设计层面天然多义。

### 3.2 同一时刻只处理一个主要输入意图

系统必须清楚知道玩家当前是在：

- 系统交互
- 地图选择
- 移动换位
- 战斗施法
- 高压快速反应

中的哪一种主状态。

### 3.3 少而稳优先于多而炫

手势数量不是卖点。对于毕业设计原型而言，最重要的是：

- 稳定性
- 可解释性
- 可教学性
- 可扩展性

### 3.4 手势必须服务玩法，不只是服务识别展示

一个手势是否值得加入，不看它“能不能识别”，而看它是否真的改善：

- 菜单交互
- 地图推进
- 战斗决策
- 表达层次

### 3.5 动态手势解决效率，不解决基础可玩性

基础玩法必须依赖静态手势就能完整成立。动态手势的价值在于：

- 更快
- 更强表达
- 更高上限

而不是成为所有玩家必须依赖的底层输入。

## 四、手势分层规范

建议将全套手势系统分成五层。

### 4.1 系统层手势

用途：

- 主菜单
- 选关
- 设置
- 教程
- 结算页

特点：

- 极简
- 低误触
- 高可解释性

### 4.2 地图层手势

用途：

- 节点切换
- 路线选择
- 进入房间
- 返回上一级地图

特点：

- 逻辑与系统层接近
- 本质是“焦点切换 + 确认”

### 4.3 移动层手势

用途：

- 左右换位
- 闪避
- 突进
- 稳定停步

特点：

- 强动作语义
- 避免连续高精度映射

### 4.4 战斗层手势

用途：

- 基础法术输入
- 常规战斗循环

特点：

- 差异明确
- 容易识别
- 适合教学

### 4.5 高阶层手势

用途：

- 快速施法
- 连段触发
- 仪式感更强的特殊输入

特点：

- 不是新手必学
- 适合高压场景和高阶设计

## 五、当前主手势规范

## 5.1 建议作为主手势保留的动作

当前版本最终主方案建议围绕以下手势展开：

### 基础静态手势

- 握拳
- V 手势
- 张掌

### 基础动态方向手势

- 向左挥
- 向右挥

### 系统确认类手势

- 握拳保持
- 张掌保持

### 高阶快速手势

- 打响指

### 可选空间动作手势

- 向前推
- 防御姿态 / 稳定姿态

## 5.2 各手势主语义规定

| 手势 | 主语义 | 默认用途 |
|---|---|---|
| 握拳 | 攻击 | 火焰术 / 确认 |
| V 手势 | 控制 | 冰霜术 |
| 张掌 | 防御 | 护盾术 / 返回 |
| 向左挥 | 向左切换 / 左闪 | 菜单切换 / 闪避 |
| 向右挥 | 向右切换 / 右闪 | 菜单切换 / 闪避 |
| 握拳保持 | 确认 | 菜单确认 / 节点进入 |
| 张掌保持 | 返回 / 取消 | 系统退出 / 页面返回 |
| 打响指 | 快速攻击触发 | 快速火焰术 |
| 向前推 | 推进 / 突进 | 接近目标 / 进门 / 脱离静止 |
| 防御姿态 | 稳定 / 停步 | 停止推进 / 战斗准备 |

## 六、Point 的定位规范

### 6.1 不再作为主控制轴

`Point` 后续不应继续作为：

- 主菜单交互核心
- 主镜头控制核心
- 主前进控制核心

### 6.2 Point 的新定位

后续可将 `Point` 保留为：

- 调试输入
- 训练模式过渡提示
- 某些过渡版本中的兼容方案

但从下一轮开始，不再把 `Point` 写入新增功能验收标准。

### 6.3 为什么要弱化 Point

原因包括：

1. 对摄像头位置敏感
2. 对玩家站位敏感
3. 更像体感鼠标，不像游戏控制器
4. 当前在代码里承担职责太多，容易形成系统耦合核心

## 七、菜单与地图交互规范

### 7.1 菜单不再基于光标点击

菜单与地图交互应从：

- 指向按钮
- 光标命中
- 停留确认

转为：

- 左右切换焦点
- 当前项高亮
- 确认进入
- 返回退出

### 7.2 推荐交互映射

- 向左挥：前一个选项
- 向右挥：后一个选项
- 握拳保持：确认
- 张掌保持：返回

### 7.3 地图交互规范

地图应设计成：

- 节点切换式选择
- 路线轮换式选择
- 单焦点结构

不建议做自由地图光标。

## 八、移动设计规范

### 8.1 移动应优先定义为“位移动作”

当前项目更适合的不是连续自由走路，而是：

- 左闪
- 右闪
- 前冲
- 停步

### 8.2 当前推荐移动语义

- 向左挥：左闪 / 左侧步
- 向右挥：右闪 / 右侧步
- 向前推：前冲 / 贴近目标
- 防御姿态：稳定站位 / 停止推进

### 8.3 镜头设计约束

如果采用这套输入方案，镜头也要同步收敛：

- 弱化精细自由视角
- 增强自动朝向或辅助镜头
- 让战斗空间服务离散动作输入

也就是说，后续玩法更适合：

- 房间战斗
- 走廊推进
- 半固定朝向交战

不适合继续强调纯 FPS 式自由瞄准。

## 九、战斗施法规范

### 9.1 基础法术输入固定

当前基础法术输入固定为：

- 握拳 -> 火焰术
- V 手势 -> 冰霜术
- 张掌 -> 护盾术

### 9.2 基础法术必须支持完整游戏循环

在高阶动作全部移除的情况下，这三项仍然必须足够支撑：

- 清怪
- 控场
- 防御
- 通关

### 9.3 高阶动作只作为增益层

高阶动作目前优先保留：

- 打响指 -> 快速火焰术

其它快速动作如：

- 指向转握拳
- 张掌横扫
- 快速冰霜 / 快速护盾挥动

都可以作为后续扩展，但不应抢占当前主方案的中心位置。

## 十、静态组合手势规范

### 10.1 可以做静态手势组合

项目允许设计“静态手势序列组合”，例如：

- 张掌 -> 爪型手 -> 握拳
- 握拳 -> 张掌 -> 握拳
- 张掌 -> V 手势 -> 握拳

这类输入属于：

- 高阶结印
- 特殊技能
- Boss 技能
- 仪式型交互

### 10.2 组合手势使用边界

静态组合手势不应承担：

- 基础菜单交互
- 基础移动
- 基础主攻击

它更适合用于：

- 大招
- 特殊机关激活
- 终结技
- 高阶关卡特殊指令

### 10.3 组合手势设计规则

所有组合手势都必须满足：

1. 每一段静态动作本身容易识别
2. 组合总长度建议不超过 3 段
3. 必须有时间窗限制
4. 每一步必须有稳定帧确认

### 10.4 当前建议

组合手势可以纳入最终版本的扩展设计，但不建议成为主玩法基础层。

## 十一、不建议作为主方案核心的手势

以下手势不建议进入主玩法核心：

- Point
- PointToFist
- 张掌左到右横扫
- 张掌右到左横扫
- 身体左移
- 身体右移
- 手部屏幕定位 / 指向命中
- 身体捕捉 / 躯干倾斜 / 站位偏移
- 双手复杂同步结印
- 画复杂轨迹
- 长链动态组合手势

### 原因

这些动作要么：

- 和现有系统职责冲突
- 对识别条件要求更高
- 对摄像头 / 场地更敏感
- 容易拖慢当前主闭环落地速度

## 十二、新增手势准入标准

后续如果要加入任何新手势，必须先回答以下问题：

1. 它解决了什么实际玩法问题
2. 它是否比现有手势更必要
3. 它是否会和系统层 / 地图层 / 移动层 / 战斗层现有手势冲突
4. 它是否适合教学
5. 它是否会显著增加识别调试成本

如果不能同时回答清楚这五个问题，则该手势不应进入当前版本。

## 十三、最终推荐结论

当前《符印守卫》的手势主方案建议收束为：

### 主手势

- 握拳
- V 手势
- 张掌
- 向左挥
- 向右挥
- 握拳保持
- 张掌保持
- 打响指

### 条件成熟后补充

- 向前推
- 防御姿态

### 高阶扩展层

- 静态组合手势（两段或三段）

这套规范的核心价值在于：

- 输入语义统一
- 菜单、地图、移动、战斗边界清晰
- 玩法表达更像游戏控制器
- 更适合后续关卡、地图和战斗系统扩展

## 十四、总结

《符印守卫》手势设计规范的核心不是把“所有能识别的动作都塞进游戏”，而是把真正值得留下来的动作，组织成一套统一、稳定、可扩展的输入语言。

从这一步开始，手势不再只是技术识别结果，而是整个游戏设计的一部分。只要这套规范立住，后续无论是改菜单、做地图、做移动，还是加入高阶结印和特殊技能，都会有清晰边界，而不会让项目重新滑回“手势 demo 堆功能”的状态。
