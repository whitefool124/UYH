# 符印守卫 新版游戏策划案 V3

## 一、项目目标

### 1.1 项目一句话

《符印守卫》是一款全程仅使用手势操作的第一人称关卡制体感施法游戏。玩家需要在地图推进、路径选择、战斗施法与生存压力之间不断做出判断，最终完成关卡目标。

### 1.2 本次 V3 改版目标

当前 Unity 原型已经具备菜单、设置、训练、战斗、结算、静态手势、动态手势和多输入源能力，但整体体验仍偏向“手势施法演示原型”。

V3 的核心目标不是简单叠加功能，而是把项目升级成一个更像“完整游戏”的体验闭环。具体目标如下：

1. 从单一防守体验升级为具有关卡目标的空间推进体验
2. 从原地施法升级为“观察、移动、选位、施法”的完整战斗决策
3. 引入地图和路线选择，让玩家拥有空间判断而非被动挨打
4. 保持项目的核心设计理念不变：全流程只使用手势操作
5. 在保证可玩性的前提下控制开发规模，适配毕业设计原型的落地边界

### 1.3 核心设计原则

- 所有核心流程必须支持纯手势完成
- 玩法必须建立在“空间决策 + 威胁判断 + 施法表达”三者联动之上
- 地图和关卡必须服务于手势交互，而不是变成独立系统堆砌
- 手势数量必须可控，宁可少而稳，不做多而乱
- 先保证一条完整、清晰、可答辩的体验主线，再考虑扩展内容

## 二、项目定位与展示价值

### 2.1 项目定位

本项目是一个面向毕业设计展示的体感交互游戏原型。其目标不是做商业化完整产品，而是验证：

- 手势识别可以构成完整游戏输入系统
- 视觉识别输出可以稳定映射到 Unity 的玩法命令层
- 地图推进、战斗决策与手势施法可以整合成一个真正“可玩”的游戏闭环

### 2.2 毕设展示价值

V3 相较于早期版本更适合毕业设计展示，原因在于：

1. 交互更完整：从菜单、选关、地图推进到战斗结算，全部由手势驱动
2. 玩法更像游戏：玩家需要做路线、位置、施法时机的判断，而不是只展示识别结果
3. 技术表达更清晰：手势系统、命令系统、关卡结构、地图设计可以形成完整论证链路
4. 演示更直观：评审能看懂“为什么需要移动、为什么需要地图、为什么这不是一个纯 demo”

## 三、目标用户与体验场景

### 3.1 目标用户

- 毕设评审教师
- 对体感交互、视觉识别、人机交互感兴趣的观众
- 首次接触手势游戏的非专业玩家

### 3.2 体验场景

- 毕业设计答辩演示
- 项目中期汇报
- 实验室原型展示
- 个人作品集展示

### 3.3 体验要求

项目需要满足以下展示要求：

- 玩家首次体验时，2 到 5 分钟内能感受到完整闭环
- 旁观者能快速理解手势如何控制地图、移动和施法
- 即使识别存在波动，也能通过界面反馈与训练流程解释系统逻辑
- 单次展示中应能体现“全手势操作”这一核心差异化卖点

## 四、世界观与关卡背景设定

### 4.1 世界观定位

《符印守卫》的整体背景不采用传统中世纪奇幻，而是采用“未来试炼空间”设定。玩家并不是在真实自然地形中冒险，而是在一个由未来技术构建、可用于战斗训练与术式测试的全息试炼环境中完成关卡推进。

在这个世界观中，所谓“施法”并不是传统魔法，而是通过手势激活高阶能量协议、战斗术式和结界系统。玩家的每一次动作都像是在空中操控一个未来战斗系统，因此手势输入、全息 UI、能量法阵和试炼关卡之间具有统一的叙事逻辑。

### 4.2 为什么采用线性推进背景

当前版本的关卡结构采用线性推进，不再以“站在原地守住一个点”为核心体验。这一决定在背景设定上也需要被合理解释。

在线性推进背景下，玩家更像是在执行一场逐段深入的试炼任务：

- 从试炼入口进入系统
- 穿过多个训练区、危险区和战斗区
- 逐步解锁更高强度的术式考验
- 最终抵达核心区域，完成终局试炼

这种背景能自然解释：

- 为什么关卡是分段推进的
- 为什么空间是模块化、规则化的
- 为什么会有出口、节点、法阵、危险区和敌人波次
- 为什么玩家需要移动而不是永远站在一个地方防守

### 4.3 玩家身份

玩家可以被设定为：

- 试炼者
- 守卫候补
- 战斗术式适格者
- 结界系统接入者

无论最终采用哪个具体称谓，核心都应保持一致：玩家是一个被投入未来试炼系统中、需要通过手势完成战斗与推进的操控者。

### 4.4 线性推进的叙事合理性

线性关卡不应被表现为“地图做不大”，而应表现为“试炼阶段逐步升级”。

建议每一段关卡都在背景上对应一个明确功能区：

- 入口校准区：建立基础认知
- 基础战斗区：掌握基础术式
- 空间决策区：学习推进与换位
- 高压试炼区：展示高阶输入与综合能力

这样即使地图是线性的，玩家也会感受到自己是在逐层深入，而不是在一个重复房间里来回打怪。

### 4.5 美术与背景统一原则

- 场景必须体现“试炼空间”而不是自然迷宫
- UI 必须体现“全息控制台 / 战斗终端”而不是普通菜单
- 法术必须体现“未来术式”而不是古典魔法火球
- 敌人必须体现“试炼系统生成的战斗体”而不是普通奇幻怪物

## 五、核心体验升级方向

V3 的核心不是“法术更多”，而是“游戏决策更多”。

本次升级后的核心体验可概括为：

1. 玩家进入一个需要推进的地图场景
2. 玩家用手势完成界面选择、路径确认和角色移动
3. 玩家在不同空间环境中面对不同类型威胁
4. 玩家根据地图结构和敌人行为选择站位与行动路线
5. 玩家通过结印手势释放法术，完成清怪、控场、防守或脱困
6. 玩家达成关卡目标后进入下一节点，形成关卡制推进

也就是说，玩法的乐趣来源不再只是“识别到动作”，而是来自以下三层叠加：

- 空间决策：我站哪里、往哪走、走不走
- 威胁判断：先处理谁、什么时候保命、什么时候推进
- 手势表达：我不是按键放技能，而是在做结印施法

## 六、核心玩法框架

### 5.1 核心玩法定义

《符印守卫》V3 是一款第一人称轻关卡制手势施法游戏。玩家以房间推进和节点选路为主线，在不同空间中完成战斗、移动、避险与目标达成。

### 5.2 核心循环

1. 观察当前地图结构与敌人分布
2. 决定前进、停留、拉开距离还是换位
3. 使用手势控制视角与移动
4. 判断当前威胁类型并选择法术
5. 通过静态或动态手势完成施法
6. 利用地图结构完成防守、突破或清场
7. 达成当前节点目标，进入下一节点或下一关卡

### 5.3 乐趣来源

项目的主要乐趣来源包括：

- 用身体动作完成施法的表达乐趣
- 在紧张压力下切换正确法术的判断乐趣
- 在地图中推进与找位的空间控制乐趣
- 每关目标不同带来的目标驱动乐趣
- 全程无键鼠完成操作所带来的新鲜感与展示感

## 七、关卡结构设计

### 6.1 为什么要引入关卡制

如果游戏只有“活下来”或“守住一个点”这一目标，玩家的行为很容易收缩成原地施法与被动应对，地图和移动系统也会失去意义。

引入关卡制的目的，是让地图、移动、敌人、施法和目标形成统一结构。每一关不仅是战斗容器，更是一个带有明确任务和节奏安排的体验单元。

### 6.2 关卡目标类型

建议当前版本优先采用以下几类目标：

1. 到达出口
2. 清除当前区域的敌人
3. 激活指定法阵或核心节点
4. 穿过危险区域到达下一个安全点
5. 抵达下一战斗节点或出口

这些目标的共同特点是：

- 容易理解
- 易于和地图空间绑定
- 能自然引导玩家移动
- 不需要太多额外 UI 与系统成本

### 6.3 推荐关卡层级

为保证毕业设计原型可落地，建议当前版本采用三关结构：

#### 第一关：教学关

目的：建立玩家对全手势闭环的认知。

内容重点：

- 菜单手势导航
- 基础移动
- 三种基础法术
- 低压遭遇战
- 一个明确出口

玩家感受应该是：
“我真的可以不碰键鼠，把这个游戏玩起来。”

#### 第二关：策略关

目的：建立空间判断和法术选择的关系。

内容重点：

- 分支路线
- 更明显的敌人差异
- 狭窄区域与开阔区域切换
- 需要移动与控场配合的战斗

玩家感受应该是：
“不是随便做动作，而是要选位置、选路线、选法术。”

#### 第三关：高潮关 / Boss 关

目的：展示项目的完整价值和技术上限。

内容重点：

- 多波敌人压力
- 范围危险区或地图机关
- 需要移动躲避和快速施法
- 静态手势与动态手势交替使用
- 最终结界保卫或核心激活目标

玩家感受应该是：
“这是一个完整的手势交互游戏原型，而不是识别演示。”

## 七、地图设计方向

### 7.1 地图设计原则

当前阶段不建议做复杂开放地图。更合适的方案是小型结构化地图，让每一块空间都服务于体验目标。

地图设计原则如下：

- 地图要让移动有意义
- 地图要让法术选择有意义
- 地图要让不同关卡目标有差异
- 地图复杂度要小于识别系统复杂度，避免开发失控

### 7.2 推荐地图结构

建议采用“房间制推进 + 轻度节点选路”的结构。

每一关由若干节点组成，节点之间通过短走廊或门连接，节点类型包括：

- 普通战斗房
- 精英战斗房
- 恢复房
- 教学变化房
- 事件房
- 出口房 / Boss 房

这种结构的优点是：

- 易于控制开发规模
- 易于安排教学顺序
- 易于做路线分支
- 易于展示关卡节奏设计能力

### 7.3 三类地图模板建议

#### 模板一：直线推进图

特点：

- 适合教学
- 目标明确
- 易于展示移动与战斗结合

玩法：

- 玩家一路前进
- 中途进入几个遭遇房
- 最后到达出口

#### 模板二：环形房间图

特点：

- 适合展示走位
- 适合多方向来敌
- 适合展示控场和护盾价值

玩法：

- 中央为保护目标或临时安全点
- 敌人从外围持续逼近
- 玩家需要绕场移动和换位

#### 模板三：双路线选择图

特点：

- 适合体现关卡决策
- 适合形成轻度 roguelike 感

玩法：

- 左右两条路难度、空间结构或奖励不同
- 玩家通过手势选择路线
- 不同路线体现不同打法倾向

## 八、移动系统设计

### 8.1 为什么移动是必要的

如果玩家只能站桩施法，地图和关卡目标的价值会大幅下降，敌人设计也会趋于单调。移动系统的引入不是为了增加操作复杂度，而是为了让以下问题成立：

- 我是否需要前进
- 我是否要换位
- 我是否该拉开距离
- 我是否要穿过危险区域

### 8.2 移动设计原则

- 不要求高强度连续挥舞
- 不让玩家长时间维持疲劳姿势
- 移动动作必须有明确语义和反馈
- 移动系统要优先服务战斗与地图目标，而不是追求拟真控制

### 8.3 推荐移动操作方案

#### 视角控制

- `Point`：控制视角方向

#### 当前原则

- 不做“长时间持续摇杆式手势移动”
- 不把移动设计成高疲劳连续动作
- 移动应服务于推进、换位、拉距、脱困，而不是成为独立高难操作系统

#### 当前冻结方案

当前版本的移动方案冻结为：

1. 四向固定距离移动
2. 不再提供独立左右转向手势
3. 提供辅助视角转动
4. 提供锁定目标切换手势

也就是说，玩家的核心移动输入是离散的“前 / 后 / 左 / 右”四向位移，而不是连续摇杆式移动。

#### 推荐输入语义

- `Point`：负责前进意图与辅助视角控制
- 左右动态动作：负责左移 / 右移或紧急换位
- 防御性姿态或确认动作：负责后撤 / 停止 / 防守语义
- 锁定切换手势：用于切换当前关注目标，降低连续精确转向压力

#### 采用该方案的原因

- 显著降低手势数量与学习负担
- 避免把移动设计成高疲劳连续动作
- 保留空间推进和站位决策价值
- 让视角控制更多由辅助系统承担，而不是要求玩家持续高精度操控

#### 约束

- 不再继续设计独立左右转向和独立回头手势
- 关卡空间必须服务于四向离散移动
- 锁定切换和辅助视角系统必须配合战斗设计一并验证

### 8.4 移动在玩法中的作用

移动系统需要服务于以下玩法场景：

- 进入战斗区域
- 靠近目标点激活机关
- 躲避高压近身敌人
- 从开阔区域退回掩体区域
- 在多波怪压力下重置站位

也就是说，移动不是装饰，而是空间决策的执行工具。

## 九、敌人与战斗压力设计

### 9.1 当前敌人设计存在的问题

如果敌人只是一种“往前冲的单位”，玩家很容易退化为站位不变的单一输出循环，地图和四向离散移动就会失去意义。

因此，V3 需要最小限度地引入敌人差异，让玩家必须做判断。

### 9.2 推荐敌人类型

#### 追击敌

- 直线逼近玩家
- 作为基础近战压力单位持续逼迫推进
- 适合用火焰快速清除

#### 冲刺敌

- 会突然加速贴脸
- 逼玩家使用冰霜、四向位移或护盾进行处理

#### 压制敌

- 能制造远程威胁或区域压力
- 迫使玩家离开当前安全格并重新找位

#### 护甲敌

- 承伤能力更高
- 适合通过控制后再集中处理，防止玩家只依赖单一输出循环

### 9.3 敌人与地图的关系

敌人设计必须和空间结构绑定：

- 开阔房间适合展示走位和优先级判断
- 狭窄通道适合展示冻结和护盾价值
- 分支路线适合让不同敌人配置形成不同体验

## 十、法术系统设计

### 10.1 基础法术保留策略

当前版本已经有三种基础法术，V3 不建议扩法术数量，而是优先强化三法术与地图、敌人、移动推进之间的关系。

#### 火焰术

- 定位：主输出、点杀、开路
- 适合处理普通追击敌和关键近身威胁

#### 冰霜术

- 定位：控场、减速、重置局势节奏
- 适合处理冲刺敌、多方向逼近和高压区域

#### 护盾术

- 定位：防御、容错、推进时的安全保障
- 适合穿越危险区域、顶住压制和高压下继续前进

### 10.2 法术与空间关系

法术设计要从“效果是什么”进一步升级为“在哪种空间里更有价值”：

- 火焰术在狭路和近距离压制中最有效
- 冰霜术在开阔区域和多方向威胁中更有价值
- 护盾术在推进、换位和穿越危险区时价值最高

### 10.3 动态手势的定位

动态手势不应只是“更炫的输入”，而应该承担明确玩法价值：

- 在高压时更快地释放关键法术
- 用于紧急反应和高光操作，而非替代全部基础输入
- 在高阶关卡中体现输入熟练度差异
- 后续双手手势作为高阶解法和高潮展示能力引入

## 十一、全手势操作闭环设计

### 11.1 项目底层原则

从进入主菜单开始，到关卡结算结束，玩家不依赖键盘和鼠标完成核心流程。

### 11.2 全流程手势覆盖范围

当前与 V3 目标中的全手势覆盖应包括：

- 主菜单导航
- 选关与路线选择
- 设置切换
- 教程与训练进入
- 战斗中的视角、移动与施法
- 关卡完成后的确认和继续
- 返回主菜单

### 11.3 为什么必须坚持全手势

“全手势操作”不是噱头，而是项目成立的核心前提。

如果地图和关卡需要键鼠完成，那手势系统就会退化为“战斗子系统”；只有让选关、推进、战斗、结算都被手势贯通，项目才能真正证明：

手势识别可以构成完整的游戏交互系统。

## 十二、手势系统规划方向

V3 后续最需要单独规划的，不是更多玩法，而是更清晰的手势系统分层。建议把手势系统拆成以下四层：

### 12.1 系统层手势

用于菜单、选关、设置与确认。

要求：

- 动作少
- 误触低
- 长时间使用不疲劳
- 易于新手理解

### 12.2 导航层手势

用于视角、移动、短位移和空间推进。

要求：

- 明确区分“观察”“前进”“闪避”
- 避免与施法动作冲突
- 保证在战斗中仍能稳定触发

### 12.3 战斗层手势

用于基础静态施法。

要求：

- 语义明确
- 差异大
- 容易稳定识别
- 支持确认机制

### 12.4 高阶层手势

用于动态动作、快速施法、组合技与未来双手输入。

要求：

- 不作为新手必学内容
- 作为高压场景或高阶体验补充
- 通过训练关逐步引入

### 12.5 规划原则

后续手势系统设计时应遵守：

1. 同一时间只让玩家处理一类核心输入意图
2. 菜单、导航、施法三类手势尽量避免语义重叠
3. 动态手势应承担“更快”而不是“更复杂”的价值
4. 任何新手势加入前，都要回答它是否真的比现有手势更有必要

## 十三、MVP 范围建议

为了保证 V3 可落地，建议当前版本的可交付范围收束为：

- 3 个关卡
- 3 种地图模板
- 4 类敌人
- 3 个基础法术
- 1 套基础移动系统
- 1 套全手势菜单与选关流程
- 1 套训练关用于介绍静态和动态手势

这样已经足够形成一个“能讲清楚、能演示、能继续做”的毕业设计原型。

## 十四、风险与边界

### 14.1 体验风险

- 如果移动过于复杂，会让玩家顾不上施法
- 如果地图过大，会削弱识别系统的展示密度
- 如果敌人太多样，会让项目成本迅速失控

### 14.2 输入风险

- 菜单、导航、施法共用手势时容易冲突
- 动态手势在不同玩家之间稳定性可能差异较大
- 长时间高举手臂会带来疲劳感

### 14.3 开发风险

- 地图、关卡、敌人、输入系统四条线同时扩张会导致开发失焦
- 若没有明确的手势系统分层，后续实现会越改越乱

## 十五、验证方式

V3 的验证不应只看“能不能识别”，而应重点验证以下内容：

### 15.1 体验验证

- 玩家是否能在 5 分钟内理解基础操作
- 玩家是否会主动移动，而不是退化为站桩输出
- 玩家是否能理解不同法术与敌人、空间之间的关系

### 15.2 交互验证

- 全流程是否真的能不依赖键鼠完成
- 菜单、导航、施法之间是否存在高频冲突
- 动态手势是否在高压场景中确实更有价值

### 15.3 展示验证

- 旁观者是否能快速看懂这是“全手势关卡制游戏”
- 评审是否能感受到地图和移动让项目明显超过普通 demo

## 十六、总结

《符印守卫》V3 的重点，不是把原型做得更大，而是把它做得更像一个真正成立的游戏。

本次升级的关键是：

- 用关卡制给玩家明确目标
- 用地图让空间决策成立
- 用移动让位置与路线有意义
- 用全手势闭环保持项目的独特性
- 用手势系统分层为后续实现和优化建立清晰边界

如果这些点成立，那么《符印守卫》就不再只是“一个能用手势施法的 Unity demo”，而会成为一个具有完整交互逻辑、玩法目标和展示价值的毕业设计游戏原型。

## 十七、美术风格方向

### 17.1 总体方向

本项目推荐采用“全息试炼空间”作为统一美术风格。玩家所处空间不是传统奇幻神殿，也不是普通现代战场，而是一个由未来技术构建的战斗训练与试炼环境。整体视觉应强调深色背景、全息投影、几何能量结构、发光边界和未来术式反馈，使手势施法行为看起来像是在操控一个高级战斗系统。

### 17.2 采用该风格的原因

1. 能强化项目的未来感与科技感，区别于普通奇幻施法演示
2. 能让“纯手势驱动 UI”和“手势施法”在视觉上更统一
3. 能通过暗背景 + 发光反馈提升战斗可读性
4. 能以较低资产复杂度构建高辨识度的展示效果

### 17.3 场景风格要求

- 场景应以规则几何结构、模块化平台和能量边界为主
- 地图边界优先使用全息屏障、光栅墙、能量立场而非厚重实体墙体
- 地面区域应通过不同发光纹路区分安全区、危险区、目标区和战斗区
- 整体色调建议使用深蓝黑、冷灰、暗炭灰作为底色，青蓝、冷白、电紫作为交互高亮

### 17.4 UI 风格要求

- UI 采用全息终端 / 战斗投影风格
- 主菜单、模式说明、结算页、目标提示都应带有半透明面板和发光描边
- 纯手势驱动的交互界面必须具有清晰的停留进度反馈和聚焦反馈
- HUD 应尽量轻量、稳定，避免厚重拟物面板

### 17.5 法术与反馈风格要求

- 火焰术：高能热能脉冲 / 橙红色离子冲击
- 冰霜术：蓝白色晶格冻结 / 低温控场效果
- 护盾术：球面能量盾 / 六边形折射屏障
- 动态手势反馈：轨迹线、投影符号、能量脉冲环、系统锁定提示

### 17.6 敌人风格要求

- 敌人应更像试炼系统生成的战斗体，而非纯写实生物
- 通过轮廓、发光核心、危险色区分敌人层级
- 普通敌、冲刺敌、压制敌、高压敌应在第一眼就能被区分

### 17.7 风格落地优先级

- 答辩版优先保证：场景基调、UI 交互风格、三法术反馈统一
- 比赛版进一步强化：敌人分层、危险区视觉、动态手势高光、高潮关视觉包装
