# 《面向体感游戏的动态手势轨迹跟踪方法实现》论文详细骨架

## 写作总定位

本文不应写成单纯的“手势分类模型训练论文”，而应写成一个面向体感游戏场景的工程型毕业设计：围绕普通 RGB 摄像头输入，构建动态手势轨迹跟踪、命令映射和 Unity 游戏交互闭环。论文主线建议固定为：**视觉输入与关键点获取 -> 动态轨迹识别 -> 语义命令映射 -> Unity 游戏系统集成 -> 实验与性能验证**。

建议全文 7 章。第 1～2 章解决“为什么做、别人怎么做”；第 3～5 章解决“我怎么设计、怎么实现”；第 6 章解决“效果如何验证”；第 7 章总结不足与展望。

## 第 1 章 绪论

### 1.1 研究背景

写体感游戏、人机交互和普通 RGB 摄像头交互的背景。重点说明传统键鼠/手柄输入虽然稳定，但自然交互感不足；体感游戏通过身体动作、手势和空间反馈增强沉浸感；普通 RGB 摄像头相比 Kinect、数据手套等设备成本低、部署方便，更适合毕业设计原型和大众化应用。

需要写清楚：动态手势不是单帧分类，而是包含轨迹、速度、方向和时序变化的连续动作。因此它比静态手势更适合作为游戏技能释放、移动、菜单确认等交互命令。

可引用材料：文献综述中关于康复、教育、体育训练、特殊教育和体感游戏应用价值的段落。

### 1.2 研究问题

本节要把问题具体化，不要只写“识别手势”。建议列出 4 个问题：

1. 普通摄像头下手部检测容易受光照、背景、遮挡和动作速度影响。
2. 动态手势存在个体速度差异、轨迹幅度差异和非线性时间变化。
3. 视觉识别结果不能直接驱动游戏，需要转换成稳定、可解释、可扩展的游戏命令。
4. 游戏交互要求实时反馈，因此必须验证 FPS、延迟、误触和触发稳定性。

### 1.3 研究目标

建议写成 4 点：

1. 设计普通 RGB 摄像头下的手势输入与关键点获取方案。
2. 设计动态手势轨迹识别与命令映射方法。
3. 在 Unity 中实现一套可运行的体感施法游戏原型《符印守卫》。
4. 通过离线视频、外部桥接、自动化测试和性能采集验证系统实时性与可靠性。

注意：如果没有完成完整 YOLO 训练，不要写“训练出高精度 YOLO 模型”。应写“引入 YOLO 前置检测模式，与 MediaPipe 关键点提取进行组合验证”。

### 1.4 主要工作与创新点

建议分成工程创新和应用创新：

- 构建 Mock、Native MediaPipe、ExternalBridge 三输入源统一抽象。
- 将手势识别结果抽象为 `GestureFrame`、`GestureCommand`、命令历史和序列匹配。
- 实现动态手势事件，如 Swipe、Snap、PointToFist、BodyShift。
- 将动态手势命令接入 Unity 游戏中的移动、施法、菜单和 HUD 反馈。
- 新增性能采集与 YOLO/MediaPipe 离线 benchmark，为论文实验章节提供 CSV 证据。

## 第 2 章 相关技术与研究现状

### 2.1 体感游戏应用现状

写体感游戏在娱乐、康复、体育训练、教育干预中的应用。重点是说明体感游戏不只是娱乐，它对交互自然性、用户参与感和动作反馈有实际价值。

需要材料：文献综述中关于老年认知干预、自闭症儿童、ADHD、康复训练、体育课堂的综述内容。

### 2.2 视觉手势识别技术

按技术路线写：

- 传统视觉：肤色分割、背景差分、轮廓特征。优点是简单，缺点是抗干扰弱。
- 深度学习检测：YOLO 系列可用于手部或人体区域定位，优点是复杂背景下定位能力强。
- 关键点估计：MediaPipe Hands 可输出 21 个手部关键点，适合实时应用。
- YOLO + MediaPipe 融合：YOLO 提供区域定位，MediaPipe 提供细粒度骨架，二者结合能兼顾定位鲁棒性和关键点表达。

### 2.3 动态手势轨迹建模方法

说明动态手势需要处理连续帧数据。可以写三类方法：

- 基于规则的轨迹识别：用位移、速度、方向、时间窗判断 Swipe / Snap 等动作，优点是实时、可解释。
- 传统滤波与跟踪：Kalman 滤波、匈牙利匹配可用于轨迹平滑和目标关联。
- 深度时序模型：LSTM / Transformer 可建模复杂序列，但训练成本和数据需求更高。

本文当前实现重点应写“规则 + 时间窗 + 命令历史”的工程方案，深度时序模型放在展望中。

### 2.4 游戏交互系统评价指标

写清楚论文实验不只看分类准确率，还要看交互指标：

- 平均 FPS。
- P95 帧耗时。
- UDP 包间隔。
- 估算链路延迟。
- 动态命令触发次数。
- 手部检出率。
- 任务完成率或误触率，如果后续补人工测试可以加入。

## 第 3 章 系统需求分析与总体设计

### 3.1 应用场景

介绍《符印守卫》：一款面向毕业设计展示的第一人称体感施法原型。玩家通过手势完成菜单、训练、移动、施法、战斗和结算。

需要说明为什么选择游戏场景：游戏对实时性、反馈和误触容忍度敏感，适合验证动态手势轨迹跟踪方法的实用价值。

### 3.2 功能需求

建议按模块写：

- 输入功能：支持 Mock、Native MediaPipe、ExternalBridge。
- 识别功能：支持静态手势和动态手势。
- 命令功能：将识别结果转换为移动、施法、菜单等语义命令。
- 游戏功能：移动、施法、敌人生成、生命、护盾、胜负结算。
- 调试功能：HUD、摄像头预览、手部骨架、动态事件显示、性能统计。

### 3.3 非功能需求

重点写：

- 实时性：输入到反馈需要低延迟。
- 稳定性：摄像头或原生链路失败时有 Mock 兜底。
- 可扩展性：新增手势或输入源不应影响玩法层。
- 可测试性：场景生成、输入适配、识别规则和数据集校验可自动测试。
- 可复现性：依赖版本、测试脚本、benchmark CSV 可归档。

## 第 4 章 动态手势轨迹跟踪与命令识别方法

### 4.1 数据结构设计

写 `ExternalVisionFrame`、`GestureFrame`、`GestureCommand` 的作用。

- `ExternalVisionFrame`：外部 Python/UDP 输入帧，包含手是否存在、手势标签、置信度、timestamp、handLandmarks、poseLandmarks。
- `GestureFrame`：Unity 运行时统一手势帧，屏蔽输入来源差异。
- `GestureCommand`：游戏语义命令，分为 StaticPose 和 Motion。

### 4.2 多输入源统一

写三条输入路径：

- Mock：用于无摄像头开发、答辩兜底和自动测试。
- Native MediaPipe：Unity 内原生关键点识别路径。
- ExternalBridge：Python 视觉桥接路径，通过 UDP 进入 Unity。

说明 `GestureInputRouter` 如何统一暴露 CurrentSnapshot、CurrentGestureFrame、CurrentGestureCommand。

### 4.3 静态手势识别与确认

写 Fist、VSign、OpenPalm、Point 等静态手势如何映射到火焰、冰霜、护盾、移动/视角语义。说明稳定确认机制可以降低误触。

### 4.4 动态手势轨迹识别

写当前实现的规则：

- Swipe：基于掌心横向/纵向位移、垂直漂移、持续时间和速度阈值。
- Snap：基于拇指和中指距离从接近到释放的时间窗。
- BodyShift：基于肩部/髋部中心点位移和可见度。
- PointToFist：从指向到握拳的状态变化。

本节建议放一张“动态识别流程图”：输入 landmark 序列 -> 历史队列 -> 阈值判断 -> 冷却时间 -> MotionGestureEvent。

### 4.5 命令历史与序列匹配

写 `GestureCommandHistory` 和 `GestureSequenceMatcher`。说明它们支持未来组合技，例如 Point -> Fist -> Snap，也能验证顺序错误和超时拒绝。
