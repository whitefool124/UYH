# 动态手势轨迹跟踪优化补充材料 2026-05-29

## 可写入论文的位置

建议补充到第 4 章“系统设计与实现”和第 5 章“系统测试与分析”中，作为动态手势轨迹跟踪方法的工程化实现与优化过程说明。标题可使用：

- 面向体感游戏的动态手势轨迹跟踪与防误触策略
- 基于手部关键点轨迹的四向扫动识别实现
- 动态手势输入链路的性能监测与交互反馈优化

## 今日开发形成的有效内容

1. 四向扫动识别从“手部位移触发”调整为“指向手势约束下的轨迹触发”。系统不再要求手部跨越屏幕中线，而是在任意屏幕区域内根据轨迹方向、移动距离、速度、路径稳定性和 Point 指向比例综合判断。

2. 防误触策略由“窗口内出现一次 Point 即可触发”升级为“起手为 Point 且窗口内 Point 样本占比达标”。其中横向扫动采用更宽松的 Point 占比以适配左右扫的识别抖动，纵向扫动保持更严格比例以降低误触。

3. 横向扫动轨迹点由掌心中心改为食指尖 SwipePoint。该改动更贴合“指向扫动”的动作语义，也减少掌心估计在横向挥动时造成的方向漂移。

4. 增加 2 秒扫动冷却，并同步修正脚本默认值、识别配置和 Unity 场景序列化覆盖值，避免运行时仍使用旧冷却参数。

5. 增加手部捕捉点的屏幕级视觉反馈。反馈点优先显示食指尖，并进行平滑与短时预测，用于缓解摄像头/MediaPipe 输出间隔带来的视觉抖动。

6. 增加性能采集与 CSV 导出，记录摄像头 FPS、Native 输入 FPS、Native 结果 FPS、处理延迟、手部更新间隔 P95 和各类动态手势触发数量，用于分析“丢帧导致动作无效”的原因。

## 可写入论文的实现描述

动态扫动识别模块维护最近一段时间内的手部关键点历史序列。每个样本包含时间戳、掌心位置、食指尖位置、手势类别以及拇指/中指等用于其他动作识别的关键点。系统首先剔除短时抖动样本，再在历史窗口中枚举可能的起点，根据终点与起点之间的位移向量判断候选方向。

对于四向扫动，系统使用如下约束：

- 最小样本数约束，避免单帧跳变被识别为扫动；
- 最小位移与最小速度约束，保证动作具有明确动态特征；
- 主轴占优约束，保证横扫不会被斜向或纵向动作误触；
- 路径稳定性约束，统计反向移动量和路径效率，过滤来回抖动；
- 指向手势占比约束，要求扫动起手为 Point 且窗口内 Point 样本比例达到阈值；
- 冷却时间约束，防止同一次动作在短时间内被重复消费。

在横向扫动中，系统采用食指尖作为主要轨迹点；在纵向扫动中仍采用掌心位置，以兼顾动作稳定性和方向可解释性。

## 可写入论文的实验分析

性能采集表明，摄像头实际输出帧率长期低于请求帧率，典型值约为 10 至 12 FPS。MediaPipe 结果 FPS 和手部更新间隔会直接影响动态手势触发稳定性。当手部更新 P95 明显升高时，玩家会感知到捕捉点停顿，进而出现“动作已经完成但系统没有及时捕捉”的现象。

今日采集中的典型对比如下：

| 采集文件 | 摄像头 FPS | Native 结果 FPS | 手部平均更新 | 手部 P95 更新 | 现象 |
| --- | ---: | ---: | ---: | ---: | --- |
| gesture_performance_native_20260529_032953.csv | 11.738 | 7.406 | 186.247ms | 723.373ms | 明显卡顿，动态触发少 |
| gesture_performance_native_20260529_033718.csv | 10.703 | 17.609 | 74.290ms | 243.958ms | 整体恢复，但横扫不均衡 |

该结果说明，单纯减少输入帧处理并不一定改善交互体验；在当前 Unity WebCamTexture 与 MediaPipe CPU 图配置下，保持较高的结果输出节奏对体感反馈更重要。因此后续优化应围绕“链路分段采样”和“丢帧定位”展开，而不是只观察整体 FPS。

## 后续丢帧定位方案

下一步建议把输入链路拆成以下阶段分别计时：

1. 摄像头阶段：记录 WebCamTexture.didUpdateThisFrame 的真实间隔、分辨率、设备名和请求格式。
2. 纹理读回阶段：记录 TextureFrame.ReadTextureOnCPU 的耗时和失败次数。
3. MediaPipe 输入阶段：记录 AddPacketToInputStream 的时间戳和排队间隔。
4. MediaPipe 输出阶段：记录 landmarks 输出、handedness 输出和 output_video 输出的间隔。
5. 识别阶段：记录 Point 分类结果、Point 占比、候选轨迹距离、速度、主轴占比和失败原因。
6. 消费阶段：记录手势事件是否被冷却、是否被移动系统消费，以及是否因同一 TriggeredTime 被去重。
7. UI 阶段：记录捕捉点显示的原始坐标、平滑坐标和最近一次识别结果年龄。

最终可以在 CSV 中增加 failure_reason 字段，例如：

- no_point_start
- low_point_ratio
- short_distance
- slow_speed
- axis_not_dominant
- unstable_path
- swipe_cooldown
- stale_camera_frame
- mediapipe_result_late

这样可以把“动作无效”从主观体感拆解为可统计的失败类型，既能指导继续调参，也能作为论文中系统测试与改进分析的依据。
